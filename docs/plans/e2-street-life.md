## What the baseline already does

`DwellPlanner.QueueAtOpening` plans customer queues independently of the optional percentage, with dry lead 2–10 minutes and rain lead 2–5 minutes; rain removes roughly half the prospective queuers. Work/study waiters do not queue. Standing bodies retain occupied slots across weather replans. Queues are derived from the waiting state, not saved optional-stop records.

`OptionalStopScheduling` overlays admitted activities without adding a visit or journey. Work breaks start halfway through the remaining admitted window (5–10 minutes); window shopping lasts 1–3, park-edge resting 10–40, paired chats 10–30 and passing audiences 2–8 minutes. Only the final walking leg of an existing shop/leisure arrival can initiate an audience. No new trip targets a performer. Conversations require two identified visitors, two distinct spots and two chances. Work assignments represent simulated activity, not native employment.

Rain refuses new optional stops and cancels existing records, including future breaks. Cancellation never restarts a stop when rain clears. Food-owned shops and meal trips take priority. A saved stop retains its original start/end, geometry, membership and activity continuation. Logical stops can outnumber physical bodies; the existing default 48 / maximum 256 pedestrian caps and four admission attempts per update remain unchanged.

New tests extend the existing scheduling, handoff, food and dwell files. The existing share/routine/settings suites continue to cover conservation, pass-on, recipient exhaustion, repeated visits, configuration and deterministic draws; they are not replaced. The exact identity is `draws = realised + (closing pending - opening pending) + drops`, not an assertion that every short window realises exactly 25%. Night uses the same draw and bounds. See the [coverage matrix and measured costs](../../CHECKS.md#e2a-street-life-proof--31-october-2026-offline-only).

## Concrete E2b red cases and limitations

These are observations/proposals, **not E2a fixes**. `python tools/optional-stop-regression/run.py --findings` prints R1, R2 and R4 without asserting that the proposed behavior already passes. The regular gate contains no intentionally failing tests. Each E2b change needs its own before-red/after-green proof and must retain chance accounting, saved continuation and current caps.

1. **R1 — future break lost to transient rain (candidate visibility change).** Minimal repro: admit a dry work visit; a saved break starts at minute 160 and ends 165; rain starts at 100 and ends before 160. Candidate E2b expectation: the already scheduled break can become visible at 160 if it is dry and safe then. Actual: `RefreshOptionalStops` cancels it at 100; it stays cancelled at 160, including on reload. The baseline deliberately implements any-rain cancellation, so this is not a newly discovered violation of the existing rule. Proposed bounded change for E2b review: apply rain cancellation when a future break becomes active, while continuing immediate rain cancellation for active stops; do not redraw, refund or extend the saved start/end, and retain closure/food/partner safety. Use existing fields only. Rig must establish whether the missed break is a visible problem before choosing this change.
2. **R2 — ambiguous frontage selects by controller order (source/double red).** Minimal repro: two active established controllers have the same sampled entrance within 0.1 m; one nightclub, one coffee shop. Desired safety result: ambiguous ownership is unavailable. Actual `NativeDoorPresent`: nightclub-first accepts chats, coffee-shop-first refuses; the first match is cached. Repro output is `True` / `False`. No claim that such a scene was encountered natively. Proposed bounded fix: resolve a unique address/controller match when publishing/rebinding the existing venue cache, refuse conflicting matches, reuse the result; no per-frame reflection or new polling. Verify real entrance/address multiplicity on the rig before mapping any new venue. No identity or schema changes.
3. **R3 — separate native business-frontage population may overlap (needs rig).** `StationaryCrowds` patches only `StationaryAiSpawner.Spawn(Vector3)`; `AmbientPedestrians` patches the ordinary walking pool. The inspected DLL has another path: `BuildingOutsideHangoutZoneController` reads `hasPedestriansOutside`; `BuildingOutsideHangoutZone` configures `AiSpawnerForBuildingOutsideHangoutZone`, which can obtain its own `BuildingOutsidePedestrian` bodies. Desired result: no additional anonymous frontage standers overlapping identified chats/queues. Actual source result: these distinct spawn methods are not targeted by the current hooks. **Whether the relevant assets enable it and whether duplicates actually occur is unproved.** Repro on rig: record type asset flag/pool, open nightclub/frontage, enumerate body/spawner ownership, compare identified stop IDs and observe entrance clearance. Proposed E2b response if confirmed: first refuse overlapping optional chat frontages using a cached, read-only ownership fact; any native suppression change needs a separate narrow hook proof preserving performers/homeless and native business actors. Do not merge a broad global spawning disable.
4. **R4 — “committed opening queue keeps its lead” is not a saved contract.** Minimal repro: `queue0`, seed 17, opening 540, same waiting visit; dry start 531.7137, rain start 535.6426. Desired plan wording: an already committed visible queue retains its lead. Actual: `QueueAtOpening` is recomputed from current rain; there is no saved queue-lead field. Occupied spots are protected by `AssignQueueSlots`, but a reload does not preserve the original weather/lead. Proposed bounded E2b work: preserve an already visible binding's queue commitment until opening, while using the existing rain lead for new queue admissions; separately prove what can be reconstructed from existing wait/visit fields after reload. A reload-wide frozen-lead promise cannot be made from a transient binding cache alone. If existing fields cannot establish it, keep the explicit reconstruction limitation; no schema addition in E2b and no chance-key change. Weather replanning itself is existing behavior, not an E2a regression.

No duration defect or night-rate defect was established. Existing bounded stops, chance conservation, pass-on, food priority, paired cancellation and physical return pass the expanded proofs. Arbitrary mid-route performer interception, animation variety and continuous preservation of a native performer's pooled body are not claimed.

## Offline cost and diagnostics boundary

`run.py --performance` runs facade doubles plus a disposable instrumented copy of the actual Core occupancy loop, actual simulator admissions and source-extracted physical selector. Fixture construction is outside timing; 60 complete admission batches/arm and 200 selector/facade batches/arm use seed 17, 48/256/957 residents, eight spots/venue, and 25/100. Cold facade sampling is counted, not timed as native NavMesh work. Selector fixtures consume at most four admissions per call and never exceed the existing 48/256 caps. No instrumentation is compiled into the mod.

Final recorded 957-visit batch p95: **10.9254 ms at 25 / 14.2531 ms at 100**; occupancy record visits **46,858 / 2,049,686**, spot queries **458 / 1,914**. These simultaneous whole-batch costs are not ordinary per-frame mod-work. All final recorded samples are below 30 ms; an earlier exploratory run had **two 100%-957-batch samples >=30 ms, max 32.6453 ms**. That earlier version printed count/max only, so its second exact duration was not captured; the final tool prints each flagged sample. Neither run measures whole-frame stalls. [Recorded output and provenance](../reviews/offline/2026-10-31-e2a.txt) and CHECKS contain the full table. Host load/tiered JIT/order affect comparisons; the 25/100 arms are workloads, not an optimization before/after claim.

No production path was edited, so there is no new per-frame reflection, polling, scan, allocation or diagnostic cost. The existing facade key/string allocations and optional refresh/occupancy costs were inspected and measured; a cache/refresh rewrite is outside E2a's behavior-identity constraint and remains parked with physical population, closure refresh and serialization. No cheap production optimization was taken; no invented before/after win is entered in the roadmap log.

An additional runtime diagnostic was optional and is omitted to keep the DLL identical. The rig can use existing bridge main-thread reads of the current simulator and physical bindings: resident ID, place/activity/phase, stop kind/spot/target/start/end/cancelled/members, `ActiveAt(state.Minute)`, optional-return state, queue bindings/slots, and `OptionalStopChances`. Group/count in the observer only when called, with bounded output and a truncation count; do not call native registration/spawn helpers or mutate population state. Report scheduled future, active, expired, cancelled, approaching, standing and returning separately; logical realised stops are not proof that bodies stood visibly.
