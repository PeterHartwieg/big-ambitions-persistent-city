### 2.2 Native save contract (read-only ILSpy inspection, installed `BigAmbitions.dll`)

`SaveGameManager.Save(SaveType, string, string)` returns false if `CanSave()` refuses. Otherwise it joins any running `_saveGameSaveThread`, sets `_saveProcessesRunning = 2`, and invokes `GlobalEvents.onSaveGame?.Invoke()` synchronously (a plain `Action` field, not `InvokeSafely`). It then calls `PortraitGenerator.Create` and `GenerateSaveGameTexture` (an asynchronous camera capture whose callback decrements `_saveProcessesRunning`), followed by `File.Delete` of a temp path and private static `SerializeSaveGame(object)` **synchronously on the main thread**. Its argument is a private `SaveGameThreadWrapper { Path = <temp path>, SaveGame = Current, SaveAsJson }`, where `Current` is a `GameInstance` whose `public Dictionary<string,string> modData` holds every mod key. `SerializeSaveGame` catches and logs every exception itself, so `Save` returns true even if serialization failed. Only after that does it start `CompressSaveGame` on a "SaveGame Compress Thread", and then it writes the `.meta` file. `SaveGameSerializationHelper.CompressBinaryData(path, outputPath)` opens `new GZipStream(File.Create(outputPath), ...)` and copies the temp file into it. That compresses **directly over the destination save file** (no temp-and-rename), so a save that reuses a name (`Recover Midnight`, a recover slot, a manual overwrite) truncates the existing file in place. A kill during compression can leave a truncated save at that path; the native game does not preserve the previous file. F7 cannot change this without a native hook on file replacement, which it refuses. `SaveType` is `Default`, `RecoverSave`, `OldAgeBackUp` or `MidnightSave`. A separate `LoadAsync` relocation branch calls `CreateSaveSnapshot(Current)` (Odin `SerializationUtility.CreateCopy`) and runs `SerializeSaveGame` on a "SaveGame Serialisation Thread". That branch does not invoke `onSaveGame`.

Consequence: the native save epoch is that one synchronous `Save` call. Every `modData` key the game writes to disk is read during `SerializeSaveGame`, after all `onSaveGame` subscribers have returned and before control returns to the frame loop. No simulation `Update` runs inside the call. Native money, orders and stock, PC receipts and the authority manifest are therefore captured at the same instant as the PC payload, **provided the payload is complete in `modData` before `SerializeSaveGame` starts**.

### 2.6 Boundaries and invariants F7 must keep

- **Native sale authority.** Native inventory, orders, receipts and hourly/daily settlement remain authoritative. `BuyLive` revalidation, one `ProcessCustomer` per sale and `BusinessHelper.ProcessDailyOrders` as the sole revenue path are unchanged. F7 never books, replays or reconstructs a sale.
- **Duplicate-sale protection.** Receipts stay in their own live `modData` keys. A `Pending` or `Conflict` receipt is never retried or cleared by a save, migration or encoding change.
- **Exact money.** Integer minor units ([native-money rules](../decisions/2026-10-28-native-money.md), `MoneyJson`). No float or decimal round-trip on the wire.
- **F1 boundary.** `BeginAccountingObservations` runs before any save observation. Epoch drain is checked with `IsAccountingEpochDrained`/`IsCaughtUpTo` (`Core/CitySimulator.cs:172–200`). Minute equality is never proof of drain. The `accounting-stop_v1` marker and the load-time `Compatible` refusal stay.
- **F3 bounded units.** Posting units (≤32), the route-input lease and finite route continuations, the pending-route clock barrier (`PlanningPending`, `Core/CitySimulator.cs:21–23`) and the rule that an explicit save completes captured campaign work. No saved cursor exists and F7 adds none: posting queues rebuild from each budget's next-posting timestamp, and a pending route event reruns from its timestamp.
- **Identity.** Stable ordinal IDs. No identity change on reload, cadence or encoding change (AGENTS.md).

### 3.2 Separate runtime storage from the wire format

The wire format today *is* the runtime object graph, so every save walks and validates the full mutable graph and every schema change edits runtime types. F7 adds a persistence layer with three parts:

1. **Runtime model** (Core). Stays the authoritative mutable simulation state with its existing semantics. F7 changes it only where a change is both a save win and safe: committed routes become immutable after commit (section 3.4).
2. **Save snapshot** (Persistence, new). An immutable, detached projection of exactly the state the wire must carry. It holds primitive arrays, interned ordinal string tables, shared immutable route references and exact money integers. It holds no references to native objects and no mutable runtime lists. It is captured on the main thread inside `onSaveGame`.
3. **Wire codec.** It encodes a snapshot, and decodes into a snapshot that is then materialized into a runtime `CityState`. Frozen readers keep decoding their own shapes. F7c first proves the split with the **existing writer-25 bytes**, then F7d adds a compact encoding as a new schema.

Validation moves onto the snapshot. Most structural rules (bounds, ordering, references resolving inside tables) then hold by construction during capture, and the remaining semantic rules (money conservation, roster/factor, journey/queue consistency) run over flat arrays. The strict reader is not weakened: load still checks the full shape and semantics.

### 3.3 One exact save epoch

**Definition.** A save epoch is one invocation of native `SaveGameManager.Save` that reaches `SerializeSaveGame`. Native accounts, stock, orders, PC receipts, the authority manifest, the accounting-stop marker and the PC payload are consistent only if all of them are read from `GameInstance` state frozen between the start of the `onSaveGame` callbacks and the start of `SerializeSaveGame`.

**Rules (F7b):**

1. *Capture point.* The PC snapshot is captured inside the `onSaveGame` callback, after `BeginAccountingObservations`, `BeforeSave`, `CompleteCampaignsForSave` and `RefreshKnownOwnership`, and after the epoch check. These are today's steps, kept in order.
2. *Publication point.* The encoded payload must be assigned to `modData` before `SerializeSaveGame` reads it. In the baseline design this happens before the callback returns, as today. The only permitted variant is F7e (section 3.5).
3. *No stale snapshot.* A snapshot captured in an earlier frame, an earlier save, or before any of the step-1 observations is never published. Each snapshot carries the save sequence and the native `GameInstance` identity it was captured for. Publication refuses a mismatch.
4. *No concurrent traversal.* No thread other than the main thread reads runtime state. A worker may read only the immutable snapshot.
5. *Re-entrancy.* If `onSaveGame` fires while a PC event unit, checkout or initialization is executing on the call stack, or while initialization has not completed, the callback refuses publication and writes the failure marker (rule 6). It does not take a mid-unit snapshot. Native `Save` and PC `Update` are both main-thread and are not expected to nest; the guard turns that expectation into a tested contract.
6. *Epoch side key.* A new versioned key `persistentcity:save-epoch_v1` is written in the same callback, **after** the payload. On success it holds the save sequence, the payload's exact character length, the writer schema, the population key and the snapshot minute. On any capture, validation, encode or publication failure it holds `failed:<sequence>`, and the previous payload stays unchanged (never deleted). On load, a marker that does not describe the present payload, or a `failed` marker, refuses PC start, preserves every key and reports the reason. **Compatibility with writer-25 binaries.** The base and every build before F7b ignore `save-epoch_v1`. A refusal must therefore not depend on that key alone. Every F7b failure (capture, validation, encode, publication, re-entrancy) **also** goes through the existing F1 `StopAccounting` path, which writes `persistentcity:accounting-stop_v1` (`Persistence/AccountingStopStore.cs:9–12`; startup refuses on key presence, including an unknown value, via `CanStartAccountingSave`) and releases food ownership at the next native boundary. F7b writes a distinct stop value (`save-epoch-failed`) for diagnostics. Base binaries refuse on presence alone, so a failed save is refused by every build. Recovery is to load an earlier unmarked save; a marked save line stays stopped, as F1 already specifies. **The callback never throws into native `Save`.** `onSaveGame` is a plain `Action` (not `InvokeSafely`), so an escaping exception would abort native `Save` partway through. At the base, `StopAccounting` reached from `BeginAccountingObservations()` runs outside `Save()`'s try/catch, and `NativeFoodOwnership.ReleaseAfterAccountingFailure()` can throw `InvalidOperationException` after the marker is written. F7b wraps the whole callback, including that path, so it writes both markers first, then catches every exception, records it and returns normally. The side key is only *added* evidence: newer builds also refuse a success marker that does not describe the present payload. A payload with no marker (all saves before F7b) loads under today's rules, including the minute-granular `AccountingClock.Compatible` check. An unknown marker version refuses and preserves.
7. *Why a marker as well as the minute check.* Today a failed write leaves the previous payload, and the load-time `Compatible` check refuses it only if the native clock moved past that payload's minute. Two saves inside one native minute (a manual save after a midnight save, for example) can pair a same-minute stale payload with newer receipts. F7b's first test establishes whether receipt reconciliation already makes that safe. The marker removes the dependency in either case. This is a gap to measure, not an observed defect.
8. *Receipts and the manifest are not copied into the payload.* They are already native-side keys in the same `modData` and therefore in the same epoch. F7 adds no second copy that could diverge.
9. *Detach outside a save.* `Fail` (`Runtime/PopulationLifecycle.cs:7–12`) calls `Detach` (`Runtime/PersistentCityMod.cs:681–691`), which unsubscribes `onSaveGame`. After a runtime failure outside a save (physical, RLO or Update), every later native save keeps the last good payload N with its matching marker N while native money, receipts and the manifest move on. A matching marker cannot show that staleness. So every detach of an attached session **while its `GameInstance` is still `SaveGameManager.Current`** also writes the accounting-stop marker (with value `detached-after-save`) and `failed:<sequence>` into that live `modData`, and any later native save of that city carries the refusal. This includes `Fail`, `StopAccounting` and `Shutdown`: `Shutdown` is reached from `GlobalEvents.onGameUnloaded` (subscribed at `Runtime/PersistentCityMod.cs:615`, so every ordinary return to menu), from `PersistentCityMod.OnUnloadAsync` (`:40–44`) and from `PopulationRuntime.OnDestroy` (`:710`), and it neither clears `SaveGameManager.Current` nor prevents native saves. The only exemption is a **verified retired or replaced save object**: the session's bound `GameInstance` is no longer reference-equal to `SaveGameManager.Current` (for example `ResetPopulationForSaveChange` after a different save loaded, or `Current` null after scene unload). In that case nothing is written, because the stale object can no longer reach native `SerializeSaveGame` through `Save`. The native order between `onGameUnloaded` and any later `Save` of the same `GameInstance` has **not** been inspected, so ordinary game unload is not treated as a verified retirement. The marker write stays. Writing into the in-memory `modData` of an unloading city is harmless unless a native save of that object follows, because the save files already on disk are unchanged. F7b and rig check 1 must show that a normal save followed by quit to menu leaves that save loadable, with no stop marker. If either shows that a save of the same object can follow `onGameUnloaded` (exit-save ordering, or `Current` reused), F7b must instead detach without markers on that path only after proving a final save already published a coherent payload and epoch marker for the current epoch. It must never let ordinary save-and-quit stop the save line.
10. *Native relocation path.* The `LoadAsync` relocation branch copies `Current` without `onSaveGame`. It carries the payload exactly as loaded, with the matching epoch key, so it remains consistent. Rig check 1 covers it.

The plan **refuses**: background snapshots taken before the save call, incremental "dirty since last save" payloads assembled from earlier frames, publishing a worker result after `SerializeSaveGame` has started, and any worker read of live runtime collections.

### 3.4 Compact references, shared immutable routes, bounded histories, immutable snapshots

- **Compact references.** Wire-local tables for place IDs, business IDs, citizen and person IDs (F5), car IDs and product names (schema 25 already has the name table). Rows refer to entries by ordinal index into the table for that save, sorted ordinally by the exact ID string. Indices are never identities, never feed seeded draws and never survive outside one payload. The decoder materializes exact strings and interns them once per load, which also reduces retained memory: today every decoded ID is a separate string instance.
- **Shared immutable routes.** A committed `Route` becomes immutable at commit: legs frozen, total minutes computed once. That removes the per-read summation and the deep route clone flagged by the October review. Snapshot capture then copies references instead of legs. On the wire, F7p measures two options: a per-save route table that deduplicates identical committed routes by exact content (exact doubles and topology ranges), and road legs encoded as directed node-ID ranges against the persisted `TrafficTopologyId` fingerprint (the existing road-tag `TopologyStart/Length` shape). Traversed portions of active routes are kept, because progress, timing, parking and validation need them (October review). Nothing is trimmed or replanned to save bytes.
- **Traffic definitions.** `TrafficKernelState.Definitions` (9,093 links in the archived October save) mostly mirrors static topology. F7p measures columnar encoding (default) against omitting definitions and recomputing them from the topology fingerprint. Omission is acceptable only if the decoder rebuilds byte-identical definitions and refuses on any fingerprint or content mismatch. Otherwise definitions stay, encoded columnar.
- **Bounded histories.** Every retained history already has a bound: 64 recent visits per citizen (`MaxRecentVisits`), 3 meal outcomes, 4 memories per consumer, 14 days of shop history with ≤8 cells per row, 14-day outflow, receipts pruned by native day with unresolved intents protected. F7 adds no history and changes no retention. F7p reports bytes per history family so that any retention change is a separate, visible decision (section 9, Q2/Q3), never a silent prune. Migration never prunes history.
- **Immutable snapshots.** A snapshot is built once per save epoch, used by validation and encoding, and then discarded. It is never cached across saves, never reused after a later mutation, and never published for a different `GameInstance`.

### 3.5 Encoding away from the main thread, only where the native contract allows

The native contract in section 2.2 leaves one legal overlap window: between the end of `onSaveGame` and the start of `SerializeSaveGame`, the main thread runs `PortraitGenerator.Create` and the screenshot request (portrait about 146 ms in the October Mac sample). **F7e** is a conditional slice:

- In the callback, capture the immutable snapshot (rule 1), then start one encode job on a worker that reads only that snapshot.
- A Harmony prefix on private static `SaveGameManager.SerializeSaveGame(object)` joins that job before native serialization. It unwraps the `SaveGameThreadWrapper` argument and compares its `SaveGame` with the captured `GameInstance`. It never throws: an exception from a prefix would escape the method's own try/catch and propagate out of `Save`, so the prefix catches everything and falls back as below. It acts only when the call is on the main thread, inside the same `Save` invocation, with a matching save sequence and `GameInstance`. The `LoadAsync` relocation call on the serialisation thread is ignored by those guards.
- If the job failed, the prefix runs the synchronous encode as a fallback. If that also fails, it writes the `failed` epoch marker (rule 6). The old payload is never paired silently with new native state.
- The rig's save guard (a prefix on `SaveGameManager.Save` that returns false for non-default save types in flow mode) prevents both the callback and serialization, so no join is left waiting.

F7e is built only if F7a/F7c measure snapshot capture at ≤25 % of encode time **and** the native campaign shows a portrait/screenshot window long enough to matter. Otherwise the synchronous compact writer (F7d) is the design, and F7e is recorded as not worthwhile. Post-save read-back verification (strict-read the encoded payload to prove it round-trips) may also run on a worker after `Save` returns. A failure there writes the `failed` marker into live `modData` for the next save; the already-written file is still refused on load by the strict reader. Synchronous semantic validation before publication stays.

### 3.9 Historical codec maintenance

The mod is unreleased, so every older payload is a development payload: rig fixtures, disposable FT cities and Peter's test cities. Policy:

- **No reader is retired by F7.** The chain 13–17 / 18–19 / 20 / 21–24 / 25 stays. Retiring a reader needs a separate recorded decision with evidence that no needed payload depends on it. This plan does not make that decision.
- **Frozen, not edited.** Each superseded writer becomes a frozen reader (E5d pattern: `PopulationSchema24*` freezes 24's resolver, prechecks and converters). F7f moves golden fixtures for every supported schema into one corpus with pinned hashes. Each schema's reader is checked against its corpus on every run, so refactors cannot silently change old semantics.
- **No growing monolith.** F7d adds the compact writer as a new codec. The schema-25 JSON codec (and F5/F6's if they write JSON) becomes a frozen reader without change.
- **Never silently overwrite.** Unsupported, future, corrupt or overbound payloads are refused with the original string reference and every other key preserved. A refused city is not rewritten by a later save, because PC is not attached. Older than 13 stays refused and preserved.
- **Maintenance cost** is tracked in F7f as lines and test time per frozen reader, so a later retirement decision has data.

### 3.10 Assumptions about F5

F5 owns the identity model. The F7d wire format relies on the shared baseline as follows.

| Baseline | What the wire format relies on | If F5 decides differently |
| --- | --- | --- |
| **B1** one Person per independent consumer, stable `PersonId`; existing consumer IDs preserved or explicitly mapped one-to-one at migration | One person table sorted by ordinal `PersonId`; rows refer to persons by payload-local index; the F5 migration mapping is carried exactly once, in F5's schema, not repeated by F7d | If F5 keeps a separate consumer slot, the table gains a consumer sub-table keyed by (PersonId, slot). Encoding cost rises but the design holds. If IDs are renumbered without a mapping, F7 refuses that design in review, because it breaks B1 and AGENTS.md. |
| **B2** Resident or Visitor; residents in exactly one `HouseholdId` with a home; visitors have origin and stay window, no home | Household table (members as index ranges after sorting by household then person); visitor rows with bounded windows, so expired visitors leave the payload | If visitors are unbounded or retained after departure, F7 needs a retention bound from F5 before F7d can budget bytes |
| **B3** Person → Workplace employment with its own schedule; at most one wage source per employment | Employment table (person index, workplace index, schedule reference); duplicate rows refused on decode | If employment is per household, the table is keyed by household; refusal rules move with it |
| **B4** money in exactly one owner per unit; every demand unit has one owning Person | One integer balance column per owner kind (person or household, as F5 decides); every meal/intent row has exactly one owner index; decode refuses a unit with zero or two owners | If F5 chooses household wallets, the money column moves to the household table; conservation tests are unchanged |
| **B5** bodies are capped presentation; identity and money never depend on a body | Bodies and leases are never persisted beyond today's restorable lease facts | none |
| **B6** mod-owned deterministic identity, stable ordering, seeded draws, no native references in persisted state | Ordinal sort for every table; no native handles; seeds and keys exact | If F5 persists a native reference, F7 refuses it in review |

**Recommended order.** Land F7's storage/wire **separation** (F7a, F7b, F7c, all writer 25 and byte-identical) **before** the F5 population schema. Then land the **compact encoding** (F7d) **after** F5's population schema, and after F6's schema if F6 needs one. Reasons:

1. F5's migration is the riskiest identity change in the roadmap. Building it on F7c's snapshot/codec split means F5 defines snapshot DTOs once, and F7d changes only the encoding, not the entity semantics.
2. Compacting the current consumer-factor model first would spend effort on a shape F5 replaces, and would add one more frozen reader that exists only to be migrated away.
3. Sequential schemas keep one owner and one reviewed migration per writer number (the E5d/steps-B–E rule). One combined F5+F7d migration would put identity remapping and encoding change in the same failure surface.

## 5. Save schema and migration impact

Against writer 25:

- **F7a, F7c, F7e, F7f, F7p:** no population schema change. F7c must reproduce writer-25 bytes exactly.
- **F7b:** no population schema change. It adds the versioned side key `persistentcity:save-epoch_v1` in the `persistentcity` namespace with its own strict reader. An unknown version or malformed value refuses PC start and preserves all keys. Writer-25 binaries before F7b ignore the key and the population payload stays writer 25, so the key alone gives them no refusal. F7b therefore also writes the existing `accounting-stop_v1` marker on every failure and on every detach outside a save (section 3.3, compatibility policy and rule 9), which those binaries already refuse on. A successful F7b save is consistent and loads normally in older writer-25 builds.
- **F7d:** a new writer number, allocated at implementation time in merge order. It must come **after** F5's population schema and after F6's schema if F6 needs one. F5, F6 and F7d schema changes are **sequential, not combined**. Each has one owner, one reviewed migration and one frozen predecessor. F5's schema and F6's schema may be ordered between themselves as those plans decide. F7d must not precede F5's.

**Migration shape (A2/E5d style).** Read the entire source under its own frozen reader (shape, counts, identity, capability and exact-money rules). Migrate into a detached snapshot. Validate the new graph and both serialized size limits before any session or store publication. The source `modData` string stays until a later successful save replaces it. On any failure: refuse, report, keep the original string reference and every other key. IDs and money are copied exactly; there is no renumbering, no rounding and no history pruning. Held inputs, receipts states, ownership intervals, D3a outflow, B memory and committed journeys carry over field for field. New algorithm adoption follows the established next-logical-day rule. Projecting migrated content back through the predecessor's frozen writer must reproduce the source bytes (E5d's check), wherever that predecessor writer still exists in test code.

**Bounds.** Caps stay: 256 Mi characters and 256 Mi UTF-8 bytes, depth 48, 4,000,000 embedded records, 50,000 citizens (F5 owns any change to the population ceiling and must budget it), 20,000 places, 512 route legs. The compact encoder counts records with the same streaming and semantic rules as today. Payload-local tables charge one record per entry. Every collection count is checked against its bound **before** allocating it. Over-cap state refuses the write (old payload and `failed` marker) or the read (preserve), never truncates. The section 3.1 targets sit well below these caps: 64 Mi characters at the 50,000×2 stress fixture is 25 % of the character cap. CF32/CF64 remain compatibility compositions. F7d must show they still encode under the caps, with lower bytes, but they are not operating budgets.

## 6. Performance

- **Gate.** The combined ordinary-play mod-work p95 stays **<5 ms**. Every mod-work spike **≥30 ms** is flagged with count, condition and component. Whole-frame and presented-frame pacing are tracked separately (F4 #91). F7 adds **no per-frame work**: no reflection, scans, polling or allocations in any `Update` path. Diagnostics are built on request. Immutable route commit costs once per committed route, not per frame, and F7c measures it on the F3 integrated replay.
- **Save is its own latency criterion**, measured only in the save-specific campaign or offline, never inside a clean gameplay window. Save samples are always ≥30 ms today and are flagged as save samples, never counted toward mod-work p95.
- **Expected cost.** These are expectations to be confirmed, not measurements. At 957×2 representative, writer-25 encode is expected below the saturated 309.69 ms max (fewer histories). F7d targets ≤40 ms synthetic. At 5,000×2 (10,000 consumers), the target scales roughly linearly with payload to ≤120 ms synthetic, against 554.66 ms saturated today. At 50,000×2 (100,000 consumers), ≤600 ms synthetic against 2,081.78 ms. At the F5 declared population, the section 3.1 typical targets apply; F7d measures them once F5 declares the population. Load is off the main thread except `CompleteInitialization`. The 1,914 / 10,000 / 100,000-consumer `StepBudget` fixture (F3 after: p95 0.0208 / 0.0229 / 0.0111 ms, 0 B median) must not regress in F7c or F7d.
- **Native size effect.** The PC string was 73.66 % of the decompressed native save in October (UTF-16). Shrinking it should also shorten native `SerializeSaveGame` and the background compressor. Only rig check 2 can show by how much.
- **Hotspots.** Of the four parked hotspots (physical population, closure refresh, optional-stop refresh, save serialization), **F7 takes on save serialization as its own scope**. The other three stay parked. Physical population selection may be taken on by F5, not by F7.
- **Perf records.** Each slice records its before/after numbers in `docs/perf/<slice>.md`, with one index line in the roadmap perf log, per AGENTS.md. Those are slice deliverables, not edits made by this plan.

## 7. In-game checks for the batched rig

Every check below runs on the headless agent rig ([PeterHartwieg/big-ambitions-agent-rig](https://github.com/PeterHartwieg/big-ambitions-agent-rig), owned by Coding Projects, read-only here; README at `25aecb0`). The rig cannot select older game builds; old-schema and large saves are built in game by the rig from historical or current PC builds (fixture library `pc-schema-N@1` and `city-50k@1` provenance, currently pending production). Existing capabilities named below are offline-tested and pending live verification on the rig (RIG-LIVE in the E5 plan). Nothing is deferred to Peter, a playtest, an unlocked console or a by-hand visual check. If the rig cannot do something, the rig gets extended.

**Checks 1–8 form the save-specific campaign.** They run only when that campaign is separately requested, never mixed with gameplay timing windows. Within it, saves are explicit and intentional. Check 9 belongs to the ordinary batched rig.

1. **Save epoch coherence (save-specific).** The rig loads a disposable FT city with an owned food shop, advances through natural purchases, then saves at four points: just after a paid sale, with a receipt `Pending`, twice inside one native minute, and after a midnight posting unit. It reloads each save in a fresh process. It reads native money, orders, stock and statement through `state`/`money`/`shop_state`/`shop_log`, the PC receipts and authority keys, and the PC payload header and epoch marker. It asserts that PC wallets, receipt states, ownership and minute describe the same epoch as native state, that the epoch marker matches the payload, and that a relocation-path copy carries the same pair. Finally it makes a normal save, quits to the main menu (firing `onGameUnloaded`), reloads that save in the same process and again in a fresh process, and asserts it loads normally with no `accounting-stop_v1` key and a success epoch marker that matches the payload. — rig-automated (existing capability: `rig flow run`, FT `save`/`load`/`state`/`money`, `shop_fixture`, `shop_state`, `shop_log`; pending rig capability: **RIG-PCSAVE**).
2. **Save phase cost on real checkpoints (save-specific).** For each of `Default`, `MidnightSave` and `RecoverSave`, on the 957-resident representative checkpoint and on the F5 declared-population checkpoint, the rig records the native `Save` total, each PC phase (from F7a diagnostics), native `SerializeSaveGame`, portrait/screenshot and the compression thread duration, plus payload characters, UTF-8 bytes and UTF-16 share of the native save. It runs before (writer 25) and after (F7d, and F7e if built) on the same checkpoint and flags every ≥30 ms phase. — rig-automated (existing capability: `rig flow run`, FT `save`/`console`; pending rig capability: **RIG-SAVEPROF**, **RIG-SAVETYPES**).
3. **Interrupted save/reload matrix (save-specific).** The rig saves and reloads at named states: pending route answer, posting units stopped after 32/64/96, held meal decision, outward excursion, campaign publication queued, physical lease visible, receipt `Pending`. Separately, it kills the process during a save in two arms. Before each arm it saves a known-good checkpoint under a **different** name and records its hash. Arm (a) kills during native serialization of the temp file; the destination must be unchanged. Arm (b) kills during compression over a reused destination name; the destination may be truncated. For arm (a) the rig asserts that the destination bytes equal their pre-save hash, then loads that destination and asserts successful coherent continuation (payload, epoch marker and native state agree; the city runs normally). For arm (b), when the interrupted destination is incomplete, the rig asserts a safe refusal (native load failure, or PC refusal with every key preserved, never a partly applied city). It then loads the separately preserved checkpoint and asserts an unchanged hash, a coherent payload and epoch marker, and normal continuation. Native file preservation is not asserted, because native code does not provide it (section 2.2). Each reload continues under a different frame cadence and budget, and the rig compares ledgers, journeys, queues, receipts and identities against an unbroken control run. — rig-automated (existing capability: FT `save`/`load`/`state`/`time`, `rig flow run`; pending rig capability: **RIG-CHECKPOINTS**, the named-state checkpoints already requested by F1 check 4 and F3 check 2).

It loads an over-cap or corrupted copy and asserts refusal with the original preserved. — rig-automated (existing capability: fixture library manifests and `pc-schema-N@1` provenance, RIG-MODSET; pending rig capability: **RIG-PCSAVE**, plus production of those fixtures).

## 9. Questions for Peter

These are player-facing only. None blocks the plan. Each has a recommended default that the slices use unless Peter picks otherwise.

1. **Should a long save show a "Saving city…" notice?** Recommended default: show a small notice only when the city part of a save takes longer than half a second, which in practice means only very large cities. If you pick "never show it", saves look the same but a large city can freeze briefly without explanation. If you pick "always show it", every save, including quick ones, gets a brief notice.
2. **How much shop history should the business panel keep?** Recommended default: keep the current 14 days. If you pick 7 days, saves get somewhat smaller, but week-over-week comparisons in the panel go away.
3. **How many past visits should a resident remember?** Recommended default: keep the current limit, so the inspector shows the same history as today. If you pick a shorter limit, saves shrink a little, but residents' "where did they go" history in the inspector gets shorter. Shop loyalty memory (four shops) is unaffected either way.

## 10. Risks and refusals

| Risk | How it fails safe |
| --- | --- |
| Compact format loses precision or an ID | Exact round-trip and decode → re-encode identity gate F7d; any difference blocks the slice |
| A stale payload is paired with newer native state | Epoch marker plus the existing minute check; mismatch refuses PC and preserves everything |
| A worker reads live state (F7e) | The snapshot is the only worker input; owner-thread assertions; F7e not built unless its condition holds |
| A native update changes the save path or `SerializeSaveGame` | F7e's prefix checks the exact signature and fails closed to synchronous encode; F7b/F7d need no native hook |
| Snapshot capture costs as much as encoding | Measured in F7a/F7c; F7e is then dropped and F7d's smaller payload carries the win |
| Budget unreachable without dropping an invariant | The invariant wins; F7p reports the measured gap |
| F5 identity design differs from B1–B6 | Section 3.10 table; F7d waits for F5's merged schema |
| Interning or immutable routes change ordinary-play cost | F3 `StepBudget` and integrated replay regression in F7c; no per-frame work added |
| Migration exceeds caps on a valid predecessor | Refuse and preserve the original; never truncate |
| Historical reader breaks during refactor | F7f golden corpus with pinned hashes |

**F7 refuses to:**

- replay or reconstruct historical purchases, or book a sale from a snapshot;
- write native rival finances or any native economy state;
- publish a stale background snapshot, an incremental payload assembled from earlier frames, or a result produced by concurrent traversal of live mutable state;
- publish a worker result after native `SerializeSaveGame` has started;
- raise codec caps, truncate collections or prune histories to meet a budget;
- delete, rewrite or "repair" an unsupported, future or refused payload;
- retire a historical reader in this plan;
- change RLO, or True City Interiors code, or deploy to Peter's ordinary saves;
- mix save timing into clean gameplay windows.
