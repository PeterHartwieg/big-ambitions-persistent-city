### Loaded definitions first; complete shop contract second

`ItemsGetter.AllItems` is actually an **`IEnumerable<Item>` view of private `ItemsDictionary.Values`**, not a public dictionary or an item-load event. `OnItemsLoaded(IList<Item>)` clears/repopulates that dictionary, adds registered `ModItemsDictionary` entries and keeps vanilla on a name collision. `RegisterModItem(Item)` can add a definition later; `UnregisterModItem(string)` can remove one. PC only observes these methods and loaded fields; it never calls registration, repairs caches or manufactures items. `GetByName(string, bool)` with suppressed errors is a lookup only, but must be guarded by catalogue readiness.

Build a bounded, detached, ordinal-name-keyed catalogue image after load/registration changes. Match each actual advertised ID and each holder/cargo ID to that image and, at capture/checkout, to the current loaded definition. Neither `ItemNameLegacyMap`, the E3 descriptors, config, an API registration, `defaultShelfItemName`, an equipment's name nor `itemsToProduce` alone establishes eligibility. The same rule applies to vanilla and mod namespaces; `ba:` is not privileged.

The following is the **safe direct-stock contract to reuse and prove in loaded play**, not a claim of completed E3 native proof. A field match is only the first layer; native supply and the existing authority/checkout layers remain mandatory.

## 2. Only real products, seasonal behavior and Q5

Acceptance requires **both** the current loaded definition and the actual shop's advertised, priced, direct-stock contract. Catalogue presence alone is insufficient; a legacy identifier, reserved E4 code, Street Food economy row or a saved historical name alone is insufficient. Never synthesize a candidate, alternative identity, price, holder, recipe or stock to fill a gap. Loaded definitions still do not prove a nutrition/meal category merely by their names.

**Seasonal decision: refuse availability-gated products for E5.** A native member exists: `ItemHelper.IsAvailableInCurrentSeason(Item)` returns true for `SeasonName.None`; otherwise it requires `PlayerPrefSettings.SeasonalDecorations` and equality with `SeasonHelper.CurrentSeasonName`. [Batch M11–M12](../archive/e3-remaining-batch.md#shared-inspected-members-and-call-sites) establish the preference read and potentially synchronous cached/Addressable season loading. `Item.GetItemNameBySeason`, `BuildingRegistration.GetListOfItemsForSale` and layout paths additionally handle replacement/sale policy; the player menu getter simply returns its cached list. One helper would therefore not prove complete current-shop availability/substitution.

Apply the batch seasonal field refusal to **all** candidate products and participating holder/bag definitions: non-None/unknown season, special-gift/seasonal-sale/AI-seasonal flag or nonempty substitution array refuses. Also refuse a nonempty takeover replacement field rather than resolve it. Missing required metadata is unverified, not None. Do not call calendar/preferences/season loaders, choose replacements or infer Christmas from an ID. This excludes some genuinely available in-season goods; that is the intentional safe failure. Candycane/christmascookies might be nonretail or ungated; actual loaded fields decide, not their names. Supporting gated goods later needs a separate availability/invalidation proof.

Steps B–E’s original Q5 defers **drink-only meal substitution, bundles and carts**; E5 Q1 below now sets the default meal policy, Q4 confirms bundle deferral and Q6 plans cart/truck support after E5. The stock rule can naturally describe a simple finished drink or a single packaged bundle sold as one native retail unit, but it proves neither “this satisfies a meal” nor a multi-entry/resource bundle. No inspected universal food-versus-drink member was established: `ItemType` has retail/service flags, and `Item.isConsumable`, `saturation`, `energy` and consume animations are not a proven food/drink taxonomy. Do not invent `IsFood` or infer a class from a name or positive saturation. E5a reports the stock-contract match separately from meal admission. Multi-entry bundles, conversions and cart/vehicle commerce fail the contract naturally; a Street Food cart is not a `BuildingRegistration` full-service shop. No cart takeover or second checkout adapter is part of E5.

Under **Peter's Q1 decision**, every non-original product defaults to `MealClass=Food`, including an ambiguous or newly loaded sold product. This is meal policy, not an inferred native taxonomy. The original three retain their established `Food` classification. Config may override each new product's class, and E5e may supply metadata below config precedence (section 3). E5b admits only `Food` entries that also pass every loaded-definition, stock, price, supply and whole-menu guard; overrides to `Drink`, `Bundle`, `NonFood` or `Unknown` exclude the product from meal admission and an advertised excluded entry still requires whole-shop refusal. Missing/invalid/wrong-type config class values are treated as absent: use valid API metadata, then the default `Food`, with one bounded diagnostic for rejected input. **With an empty override table and no API metadata, every product passing the full native stock contract in section 1 is admitted as Food**, within the existing bounds and safe ownership boundary. No per-product code change is needed; metadata alone proves no native eligibility. Bundles remain deferred by Q4.

With new items absent, original-choice weights/draws, memory and economy must replay unchanged. ### Proposed config table, not a second loader

Implement config metadata in E5c and the small public mod metadata API in **E5e**, per Q2; the default path has no integration dependency on another mod. Precedence per field is **per-product config override > mod API metadata > defaults**, preserving the original three's established classes, saved tastes and vectors. An absent or rejected config field falls through to valid API metadata, then defaults; rejected input gets one bounded diagnostic. Add one optional top-level `FoodProductOverrides` table to `config/persistent-city.json` / `PrototypeSettings`, using the existing installed `<ModRootPath>/persistent-city.json` path. This is a deliberate narrowly bounded table extension to steps B–E's fixed flat product-key families, superseding those E5 families; other settings and loader stay unchanged. Example shape only, not a config edit (dumplings explicitly forces band 2 for every resident; chopped cheese keeps the seeded draw):

```json
"FoodProductOverrides": {
  "foodtrucks:itemname_dumplings": {
    "MealClass": "Food",
    "TasteBand": 2,
    "BreakfastFitCents": 900,
    "LunchFitCents": 100,
    "DinnerFitCents": 450
  },
  "foodtrucks:itemname_choppedcheese": {
    "MealClass": "Food"
  }
}
```

| `MealClass` | `Food` for every non-original product; established `Food` for the original three | Exact enum strings `Unknown`, `Food`, `Drink`, `Bundle`, `NonFood`, at most seven ASCII characters. Missing or rejected fields follow config > API > defaults; without valid API metadata they use the documented defaults. Follow existing numeric-string/endpoint-clamp and log-once conventions; out-of-range numeric values clamp, while unusable/NaN/wrong-type or in-range fractional integers are treated as absent with one bounded diagnostic. Exact key lookup only: no case folding, trimming, aliases, suffix matching or fallback to vanilla names. Unloaded keys remain inert config metadata with a bounded diagnostic; they neither register a product nor confer native eligibility. `Food` removes only the meal-class refusal once the definition is loaded; it cannot override native type, availability, price, resources, eligibility or capacity.

Load with the city unloaded, no watcher or per-frame parsing. Resolved metadata takes effect at the **next uncaptured, uncommitted context**, including later that day. Capture effective meal-class/taste/fit inputs for each offer in the single held decision (section 4); config changes after reload cannot rerank it. Committed trips/quotes/prices/receipts keep their terms and native revalidation. Class changes affect new menu admission and existing safe whole-business handoff, without rewriting captured terms. No daily config history or per-resident product array.

## 4. Canonical identity, saves, bounds and mod removal

Canonical identity is the **exact `Item.itemName` string**, e.g. `ba:itemname_salad`, `foodtrucks:itemname_dumplings` or `foodtrucks:itemname_choppedcheese`. Use `StringComparer.Ordinal`, deterministic ordinal menu/descriptor ordering and length-delimited canonical-name draw inputs. Native collision behavior can select a different definition with the same name: revalidate the new fields and do not inherit sale permission from the old object. A mod author reusing one name for a different product is outside PC's ability to infer semantic continuity; preserve the name's history and report the definition change.

### Missing mod is unavailable native evidence, not corrupt history

On reload or unregister, a previously saved name may no longer resolve. Valid saved names/history still load as opaque facts without requiring native definitions. Mark affected shops unserviceable immediately, withdraw new captures and hand back the **whole business** through existing ownership intervals/boundary. Do not crash market construction because `FoodProducts.Known` is false, clear the scope/history, regenerate consumers or remap to another item. Keep B memory attached to its original business generation; a missing product does not create a visit/penalty by itself.

An already-paid receipt stays paid; an uncertain intent is never retried merely because the definition vanished. Ownership cannot transfer until old work has drained. Structurally bad/future saves are a different case: preserve payload and stop unsupported execution under the early guard; do not use normal missing-mod handoff as permission to run overlapping sales engines.
