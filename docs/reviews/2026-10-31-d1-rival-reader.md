## Change and boundaries

Adds pure, immutable advertised-food observation contracts and an isolated Runtime reader. The existing `FoodBusinessCatalogue` source and player path are unchanged (the original regression output remains **29 actual catalogue-adapter checks passed**). `FoodAlternativeKind` separates player/rival observations. Both advertised-only paths report stock `Unknown`; rival availability evidence is `EstimatedFromPriceAndHours`, per Peter's 31 October Q4 decision. `ObservedPlayerSupply` is a separate evidence code for a future caller with actual supply proof; this reader never emits it. There is no computed availability, quantity, throughput or service-time assumption.

Reads existing registration fields only: native business identity, address, creation day, business type and owner, advertised retail prices, open schedule slots, temporary closure and saved customer-service rating. Price conversion uses `Money.TryFromNative` and refuses nonfinite, nonpositive, too-large and imprecise binary32 values without rounding. Only `Core/FoodProducts.cs`'s three reviewed products become offers. Other advertised entries contribute only an unsupported count, even when their prices are invalid. No stock is inferred from `cachedAvailableProducts`. The door flag means a serialized entrance has a readable transform; it proves no route. Accessibility uses the existing `GamePlaces.BuildingAccessible` read. The saved rating may be a native initial default, not current staffing evidence. Temporary closure is explicit and preserves the advertised schedule for inspection; it is not a usable opening assertion.

No startup wiring, Harmony patches, frame callbacks, UI, settings, choice, enrollment, supply setup, checkout, ledger or persistence changes. No A3/B0 types or sibling code. The four parked hotspots are untouched. No game or rig work was performed.

## Identity findings and refusals

Inspected the installed `BigAmbitions.dll` read-only with the local `ilspycmd`, specifically the field metadata and lifecycle behavior of `BuildingRegistration.Reset` and `AddToPlayer`. No durable business UUID or generation field exists among the exposed registration fields. `creationDay` is only a day, and `Reset` can reuse the registration object. However, native `Reset` replaces `retailPrices`, including when resetting an existing object. `AddToPlayer` changes ownership fields and creation day. No assemblies or decompiled source are committed; the temporary local inspection output is ignored under `build/d1/`.

Consequently the cache makes **no durable generation claim**. It reuses `FoodBusinessCatalogue.BusinessIdentity` without assigning identity from a name. Internal weak controller/registration/price-collection references check continuity within one loaded-city diagnostic session; none appear in snapshots. A changed controller, registration, price collection, identity tuple or owner quarantines that place as `AmbiguousIdentity`, even when the native tuple is identical. A harmless price-list replacement is deliberately refused too. Duplicates, observed vacancy and disappearance/reappearance also quarantine the place. Quarantine lasts until disposal, with no identity transfer or tombstone eviction. A changed save object refuses the entire session. Native price/hour edits *within the retained collections* are read afresh; list replacement requires a new diagnostic session and does not establish continuity with earlier results.

These checks detect native Reset-based same-day replacements and observed ownership changes. They cannot prove an unobserved change-and-reversion that preserves every checked object and field. D2 must provide lifecycle invalidation before using these observations as durable decision or memory identities; it must not join snapshots across sessions/reloads by the returned identity or address alone. D1 installs no lifecycle hook or authority integration.

## On-demand bridge dump

The public `PersistentCity.Runtime.RivalFoodCatalogue` API is the read-only dump seam. On the game main thread, retain a diagnostic instance for the currently loaded city, call `BeginRefresh()`, then call `ContinueRefresh()` in bounded continuation units until it returns true. Each call examines at most 16 controllers by default (explicit API range 1–64). Call `ReadSelected(placeIds)` with one through eight distinct existing shop place IDs and serialize the returned detached DTO through the bridge. For example, a fixture shortlist may contain `address:<URI-escaped street>:<number>:shop`. Reuse the instance for repeated reads/refreshes, then `Dispose()` before unload/reload. No callback or scheduler is registered by constructing it. Callers must not block one frame draining all units at 20,000 places.

Refresh retains at most 20,000 distinct places over the session, including quarantine tombstones, in two indexes referencing the same entries. The 20,001st place fails the complete image; no partial image is readable. Detailed reads during a refresh are refused; completion publishes a coherent metadata inventory, while the at-most-eight details are copied at request time. No resident loop, world scan per detail, native strong reference in a snapshot, or cached detailed menu. Normal idle gameplay does no D1 work. Identity strings are structural keys created once per place; diagnostic formatting/serialization occurs only on explicit dump calls. Warm refresh builds no diagnostic strings.

`RivalRefreshGameMinutes` (proposed default 60, range 15–240) and `RivalReadsPerUnit` (16, 1–64) remain **D2 configuration work**: this unscheduled diagnostic reader needs no settings keys or clamp/log path now. The direct continuation API rejects invalid bounds rather than silently changing a requested unit.
