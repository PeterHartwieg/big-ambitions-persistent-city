# Resumable route planning, 27 October 2026

Finding 1 of the architecture performance review of the same day: route planning ran as one synchronous call inside a citizen event, so a single frame could last as long as the most expensive multimodal plan one resident needed (52 to 138 ms in the project's captures). This change turns the plan into a request that the simulator raises and the planner answers in budgeted slices across frames. Nothing about which route a resident gets, when they leave, or in what order events run has changed. Schema 13 and the saved field set are untouched.

## What changed

The simulator no longer calls the planner from inside `Step`. `CitySimulator.StepEvent` is a C# iterator that yields a `RouteRequest` wherever the old `Step`, `TryPrepareCommute`, `ChooseOptionalDestination`, `StepMealOuting` and the workplace probes behind `ResidentLifecycle.ApplyAtHome` used to call `routes.Plan`, and resumes with the answer. The helpers were split at their plan points: `DecideCommute` and `FinishCommute` replace `TryPrepareCommute` and its out parameters, `BeginMealOuting` and `FinishMealReturn` replace `StepMealOuting`, `ChooseOptionalDestination` is an iterator writing into an `OptionalChoice`, and `ResidentLifecycle.BeginEmploymentCheck` returns the ordered workplace candidates for the caller to probe one request at a time, with `AssignWorkplace` applying the first reachable one. Every side effect keeps its position relative to the plan it preceded or followed, so the planner sees the same resident state as before and the resident is updated in the same order afterwards.

Each event runs on a working copy of the resident (`CloneForEvent`), committed into the published object when the event finishes (`CommitEvent`). The copy shares the immutable identity and the route object, which events replace rather than edit, and owns copies of everything an event edits in place: the car, the commute preparation, the meal outing, the preferences and the visit list. Objects that survive the event keep their identity on commit, so a retained car or preparation reference stays valid. This is what lets the published state keep the unstarted event while a request is outstanding.

The planner contract gained an optional interface. `IResumableRoutePlanner.Begin(RouteRequest)` returns an `IRoutePlanningJob` whose `Continue(budgetMilliseconds)` performs at least one unit of work and keeps going while the budget allows; `Dispose` releases whatever the job borrowed. `IRoutePlanner.Plan` and `ICitizenRoutePlanner.Plan` are unchanged, so `GraphRoutePlanner`, every test double and every tool keep working, and `CitySimulator.AdvanceTo` drives even a resumable planner to completion inline. Only `AdvanceFrameSlice` leaves a job pending; it then reports `AdvanceResult.PlanningPending`, `CitySimulator.PlanningPending` is true, `IsCaughtUpTo` and `NoEventsThrough` report false, and the runtime drives `CitySimulator.ContinuePlanning(budget)` until it reports completion. `TryAcquirePhysicalJourney`, `TryBeginMealVisit` and `TryBeginOptionalShopVisit` refuse the resident whose event is in flight; `RebuildRoutes` abandons a pending job before building the replacement simulator.

In Runtime, `MultimodalRoutes` implements the interface with a `PlanningJob` state machine that is the former `Plan(from, to, minute, person)` cut at every native query: the home curb search and each home access walk, the direct walk, the station capture, each subway connector walk, the car access walk, the parked curb search, the destination curb search, each egress walk, each road search start and the road search itself. The synchronous `Plan` now constructs the same job and runs it with an infinite budget, so there is one code path. `RoadRoutes.Plan` became `RoadRoutes.BeginPlan` plus a `RoadPlan` whose prologue and epilogue are the old method's and whose middle advances a `TransportRoadGraph.RoadSearch` in 64-expansion slices against a Stopwatch deadline. `TransportRoadGraph.BeginSearch` returns that resumable search; `Plan` and `PlanWithTraversal` run it to the end, so the one-shot search and the sliced search share one expansion loop. The borrowed `RoadSearchWorkspace` stays reserved for the life of a `RoadSearch`; a one-shot query issued while one is suspended takes the fallback workspace exactly as a nested query did.

`PopulationRuntime.AdvancePopulation` gives a pending job the remainder of its 2 ms budget (16 ms during a hidden economy skip) per frame, counts a completed event when the job finishes, and keeps advancing while budget remains. A job always gets at least one unit per frame, so a frame spends at most the advance budget plus one atomic native query on planning. The 60-second summary gained the number of requests, slices, events completed through slicing, frames that ended with a plan pending, total and slowest slice milliseconds, the unit kind that ended the slowest slice with its NavMesh path query count, the event restart count, the number of events run inline after repeated restarts, and the road search restart count.

## Semantics

The clock is held at the in-progress event's minute. A citizen event that needs a route becomes "in progress": the simulator records it, returns `PlanningPending` and does not advance `State.Minute`, run another citizen, traffic or food event, or report caught up until the plan has been answered and the event committed, so departure minutes and event order are identical to the synchronous behaviour in simulation time whatever the frame cadence. The published state meanwhile holds the resident unstarted with `NextEventMinute` equal to `State.Minute`; a save taken then stores exactly that, and a reload (or a planner rebuild) runs the event again from its beginning. A planner exception mid-job discards the working copy, re-queues the unstarted event and propagates; the next advance retries it. A suspended road search starts over on the same snapshot if another search bumped the per-node validation generation meanwhile. A replaced snapshot is handled at the level of the whole event (amended 28 October). A job captures the road snapshot, the public access object and the station list when it is begun, not at its first slice, because the frame that answers one request of an event begins the next one, and the earlier answer was given on that state. If any of the three was replaced since, or the snapshot was current then and is stale now, the job's next `Continue` throws `RoutePlanningRestartRequired`, including on its first slice; a job begun and finished within one call never throws it. `ContinuePlanning` catches only that exception: it disposes the job, discards the working copy with everything the event did on it (earlier answers such as workplace probes and optional candidates, a home car allocated at a curb of the old snapshot), requeues the unstarted event, counts an event restart, keeps the clock held and returns false. The next advance runs the event again from its first request on the new snapshot, which is what a reload at that moment does, so the outcome depends on neither frame cadence nor a save. After three restarts of the same resident's event at the same held minute, the next frame slice runs that event inline, where every job gets an unlimited budget in one call, so a city whose snapshot keeps changing still progresses. A job started inline finishes in its first `Continue` call and cannot throw the exception; a sliced job that `AdvanceTo` resumes can, and its event is then replayed inline. `CitySimulator.EventRestarts` and `InlineAfterRestarts` feed the 60-second summary. Traffic forecasts and node validations are read live at the moment of each read, once per link or node per search, as they are inside the synchronous plan; the final `NativePathValid` still runs live on the selected path. No route winner or permission decision is cached across requests.

## Verification

Offline suite, `dotnet test tests/PersistentCity.Tests.csproj`: 1,234 passed, 0 failed, run twice on the final sources (1,218 before this change plus 16 new tests). The run with only the Core rewrite in place, before the Runtime and test changes, also passed 1,218 of 1,218, which is the first evidence that the iterator and the working copy reproduce the old `Step`.

New Core tests in `tests/ResumablePlanningTests.cs` use one pure route function behind a synchronous `ICitizenRoutePlanner` double and a resumable double whose jobs answer only after a chosen number of `Continue` calls, over a 48-resident city with three workplaces, a school, three shops and three leisure venues, some residents starting unemployed, about a third owning cars, a deterministic refusal of one request in eleven, and a fixed meal outing on day two.

- Differential (a): for k = 1, 2, 3 and 5, where the number of `Continue` calls varies per request so every stage of every event is interrupted, six simulated days through frame slices with one `Continue` per frame give byte-identical `SaveCodec.Write` output to the synchronous run at every day boundary, and so does `AdvanceTo` on the resumable double. The runs make more than 200 requests, every job is disposed, and the requests include workplace probes, shop and leisure candidates and the preference-only meal return.
- Save mid-request (b): saving at every seventh pending request, reloading and continuing on a new simulator gives the same final state as the uninterrupted run over five days (more than 30 saves); each mid-request save passes validation and round-trips, and the pending resident's `NextEventMinute` equals the held clock.
- Sliced road search (c): `tests/RoadSearchSlicingTests.cs` runs the 30 deterministic graphs and 30 queries each from `RoadSearchCeilingTests` with four ceilings, advancing the resumable search in random slices of one to five expansions, and compares path, leg durations, estimate and the exact order of `clear` callbacks with the one-shot search (3,600 comparisons, more than 1,000 of them actually interrupted). A one-shot query during a suspended search and a nested sliced search answer the same as without the suspension; an abandoned search releases its storage; the expansion limit counts across slices.
- Invalidation between slices (d): in the road ceiling harness, a job suspended inside a 300-node road search sees a one-shot plan run meanwhile, restarts that search once (road search restarts 1, job restarts 0) and returns the one-shot route; a job suspended while a native node changes, the sweep marks the snapshot stale and preparation captures a replacement, restarts once on the new snapshot and returns the one-shot route; an abandoned job leaves later plans unchanged.
- Exceptions (e): a job that throws once at a chosen request and `Continue` index leaves no pending request, a state that validates and round-trips, and the failing resident unstarted at the held clock; continuing gives the synchronous final state. The same holds for a synchronous planner throwing inside `AdvanceTo`.
- Caught up (f): while a request is pending, `IsCaughtUpTo` is false, further frame slices do nothing and hold the clock, and the published resident is byte-identical across the intermediate `Continue` calls.
- Nested requests (g): covered by the differential runs, which assert that workplace probes and optional candidates occurred, and by `FrameCadenceDoesNotChangeDeparturesOrOrder`, where two frame interleavings with different interruption patterns reproduce every `ActivityObserved` event of the synchronous run in order (more than 500 events).

## Not verified

No game was launched and no rig was touched, so the frame-time effect is not measured; the claim that no frame spends more than the advance budget plus one native query on planning follows from the loop structure and the harness slice counts, not from a capture. The restart behaviour when the station list is re-scanned every 30 seconds was not exercised in a harness (the gate and snapshot cases were). The per-frame NavMesh query count in the summary is a counter delta and was not observed in game. The checkout carries other sessions' uncommitted edits; all runs above include them.

## Follow-ups left deliberately

Food walking quotes, `FoodRouteBatch`, the diagnostic tools and the RLO pickup diagnostic keep the synchronous `Plan` API; a walking quote inside a meal decision is still one atomic NavMesh query on the main thread. The simulator loop itself still runs on the main thread; with planning now a request and answer boundary, no event in Core touches Unity, so moving the loop to a worker thread with the main thread serving native queries is possible but was not attempted. The road search slice size (64 expansions) and the event restart cap (three restarts at one held minute before an inline run) are constants, not configuration. A replayed event repeats the native queries of its earlier requests; that cost was accepted for one consistent snapshot per event and was not measured.
