# Core identities and road tags, 28 October 2026

Findings 2 and 3 of the architecture performance review of 27 October. The routine layer built and hashed key strings on every call, scanned the place list for a resident's home, rebuilt and sorted opening windows on every hours query, and split every native road tag each time a route was mapped onto traffic. All of that now happens once per resident, per place, per day or per leg, and every output is the same as before. Schema 13, the saved field set and `SaveCodec.Write` output are unchanged, and no policy version moved.

## What changed

`StableRandom.Hash` is one FNV-1a pass over the characters followed by a fixed finaliser. Hashing `prefix + suffix` is therefore the same as continuing the state after `prefix` over `suffix` and finishing. `StableRandom` gained `Begin`, `Append` (string or char), `AppendDecimal` (the characters of `int.ToString(CultureInfo.InvariantCulture)`, including the sign and `int.MinValue`) and `Finish`. With these the code reproduces every existing string key bit for bit without building the string. I did not need integer re-mixing or a per-day draw cache, because continuing a cached prefix over a day's three or four digits costs a few multiplies and allocates nothing.

`RoutineKeys` (in `Core/DailyRoutine.cs`) holds a resident's hour shift, quiet-hours offset, commute preparation and margin draws, the seed-0 employment time, and the hash states after `Id + ":shop:"`, `":leisure:"`, `":quiet-day:"` and `":leisure-day:"`. `CitizenState.RoutineKeys` is an internal field, so neither `SaveCodec` nor `JsonConvert` writes it. `RoutineKeys.For` rebuilds it whenever the identity ID or the seed differs from the one it was built from, so a reload, a reused pool slot or a changed identity never reads a stale value. `CloneForEvent` shares the reference with the working copy and `CommitEvent` copies it back; it derives only from the shared identity and the seed. The reflection fixture in `ResumablePlanningTests` checks public properties, so it does not see the field and still passes. `SelectRoutine`, `WorkOnDay`, `NextWork`, `CommutePreparationAt`, `DailyRhythm.Lookup` and `ResidentLifecycle.NextHomeEvent` read from it.

`DailyRoutine.At` has an overload that takes the resolved home `Place`. `CitySimulator` passes it from its existing place dictionary, so the leisure branch no longer scans 1,011 places by string. The old four-argument overload still scans, for tests and tools. `DestinationChoice.Choose` and `Shortlist` compute the state after `choiceKey + ":"` once and continue it over each place ID. An internal `Choose` overload walks an `IReadOnlyList<Place>` without LINQ for the routine path. `ResidentLifecycle.BeginEmploymentCheck` resolves the home through the simulator's dictionary and falls back to the old `First` scan (and its exception) when the ID is not indexed. `Population.CreateResident` hashes `identity.Id + ":home:" + p.Id` from one shared prefix as well.

Opening windows are cached per place in an internal `Place.OpeningCache` for the two most recently built days. The cache keeps an exact copy of `OpenMinute`, `CloseMinute`, the `WeeklyHours` list reference and every window's day, from and to minute, and compares them on every query. It is rebuilt when anything differs. I chose this over the hours-version counter the review proposed because several writers do not go through a setter: `GamePlaces` and `FoodBusinessCatalogue` add to the list in place, and an `OpeningWindow` can be edited in place. A version counter would miss those, while the comparison sees every one of them and costs a loop over about fourteen windows instead of ten days of window expansion plus a sort. Nothing outside my file set needs a change for it; `NativeFoodHours.RefreshRoutineHours` (where the hours refresh now lives, not `NativeFoodMarket`) needs no version bump. The cache is an immutable object swapped by reference, so a reader on another thread would still see one consistent snapshot.

`RouteLeg.ServiceId` now has a backing field, and its setter decodes the tag into an internal `RoadTag` struct: kind (`v1` or `fragment1`), the offset and length of the topology segment inside the string, and the two node indices. It decodes once when the planner sets the tag, when a leg is copied, and when Json.NET loads it. Parsing uses `int.TryParse` on spans with `NumberStyles.None` and the invariant culture, the same parser the `Split` version called on substrings, so leading zeros, overflow, signs, spaces and non-ASCII digits are accepted or refused exactly as before. The wire string is unchanged: `RoadRoutes` still writes `native:road:v1:<topology>:<from>:<to>`, now from one prefix string per plan instead of a five-part concatenation per leg. The topology is never cached. `TrafficNetwork.TryTag`, `RoadRoutes.TryTag` and `RoadRoutes.KnownPhysicalFragment` compare the tag's topology segment with their own current topology in place on every call, so a tag from another snapshot fails and the callers fall back as before. Malformed tags still fail the whole mapping.

`TrafficNetwork.TryMapCore` became `TryMapSpans`, an index walk that writes `MappedSpan` structs into a caller-owned list. The public `TryMap` and `TryMapRemaining` build the same `List<TrafficRouteLeg>` from a thread-static span buffer. The simulator's `ScheduledMinute`, `NextTrafficBoundary` and the binding check in `EnsureTrafficNetwork` only read the first unfinished span, so they use `TryMapRemainingSpans` with a buffer the simulator owns and allocate nothing. `TryStartTraffic` keeps the allocating call, since the kernel stores the legs it enqueues.

One more allocation source turned up while measuring. `CitySimulator.ValidateCarRoute` built `Identity.Id + ":car"` for every car leg of every route it validated, which is 300 strings for a 300-leg route at plan time and again at arrival. It now compares length, prefix and suffix in place.

## Queue rebuild with a request in flight

This is a separate fix inside my file set, requested during the work and found by two reviewers of the resumable planning change. `EnsureTrafficNetwork` rebuilds the scheduler queue (`due.Clear()`, then every resident not in traffic or a physical journey) when the planner's network reference changes. It did not skip the event whose route request was pending. That event had already been taken out of the queue, so the rebuild put it back at the held clock. `CompleteEvent` then rewrote its sort key while it sat in the `SortedSet`, and its `due.Add` returned false without complaint. The set ended up with the resident twice, out of order, and the clock could run backwards. `AbortPending` would have thrown "lost its queue slot". The runtime reaches this whenever a road snapshot is replaced while a job is suspended and `RefreshTrafficClosures` runs before planning resumes; `AdvanceFrameSlice` also calls `EnsureTrafficNetwork` before it returns `PlanningPending`.

The rebuild loop now skips the item for which `InProgress` is true, and `CompleteEvent` throws if `due.Add` fails, like `AbortPending` already did. `tests/PendingEventQueueTests.cs` adapts the reviewer's reproduction into four tests. One checks that the queue stays one short of the roster across a swap and is whole after the commit. One checks that a planner failure after a swap re-queues the event exactly once. One checks that the queue stays in strict order across 40 swaps and that observed event minutes never decrease. The fourth swaps the network before every suspended request for two days and requires the same `ActivityObserved` stream and the same save as an uninterrupted run. All four failed with the loop unchanged and pass with the fix. `ResumablePlanningTests.NetworkRebuildWhilePendingKeepsTheInFlightEventOutOfTheQueue` does the same on the 36-resident fixture over four days with more than 20 rebuilds, also through a frame slice taken while pending, and inspects the queue through reflection after every rebuild and commit. It failed the same way before the fix (37 queue entries for 36 residents).

## Left deliberately

`places[person.PlaceId]` and `citizenEvents[id]` remain dictionary lookups. They hash a string but allocate nothing, and resolving IDs to `Place` references at load would add transient fields that every writer of `HomeId`, `PlaceId` and `DestinationId` would have to keep in step. The review lists that as a further step; I left it.

The mapped traffic legs are not cached on the `Route`. With decoded tags the span walk allocates nothing, and a cache would need invalidation on every leg, retiming and network change for little gain. `TryStartTraffic` still allocates its list, once per admission.

`Core/TravelTiming.cs` still splits a road tag when it retimes a leg into a fragment (around line 463). That runs once per retimed leg, and the file is outside my set. `SaveCodec.IsMovingTrafficGeometry` still splits, but only for sub-micrometre car fragments during validation. Other per-resident string keys sit outside my set or run once per day: `MealRhythm`, `FoodRoutines`, `FoodHouseholdPolicy`, `FoodCommerce`, `HouseholdFinance` and `DwellPlanner`, the `":optional:"` key in `OptionalDestinations`, and the daily employment key. They can move to `RoutineKeys` or prefix states the same way if a profile shows them.

Each `RouteLeg` is 24 bytes larger for the decoded tag. In the harness below that shows up as the planner's own allocation growing from 29.1 MB to 31.0 MB over six days.

What remains of the simulator's allocation is mostly outside these two findings. It is the per-event working copy from the resumable planner (a `CitizenState`, its preferences, preparation and visit list, the `StepEvent` iterator), `TrafficRouteLeg` objects at admission, and the traffic kernel's sorted sets and linked lists, which is finding 4.

## Verification

All runs used the checkout as it stood on 28 October, including other sessions' uncommitted edits (the food work running concurrently, and a `carAtEntry` change in `Runtime/MultimodalRoutes.cs` that is not mine). The machine's load average was between 130 and 200 during these runs, so wall-clock times are not meaningful. CPU time was: the existing `SaveDuringAPendingRequestStoresTheUnstartedEventAndReplaysIt` test took 23.5 s of user CPU after the change and 24.8 s against the pre-change sources, while each took five to six minutes of wall time.

Offline suite, `dotnet test tests/PersistentCity.Tests.csproj`: 1,255 passed, 0 failed (12 min 43 s wall). That is the 1,234 existing tests, 14 new tests of mine (9 in `CoreIdentityTests`, 4 in `PendingEventQueueTests`, 1 in `ResumablePlanningTests`), and tests the concurrent food session added.

`tests/CoreIdentityReference.cs` holds verbatim copies of the pre-change `DailyRoutine`, `DailyRhythm.Lookup`, `DestinationChoice` and the three `Split`-based road tag parsers. `tests/CoreIdentityTests.cs` compares the production helpers with them:

- The incremental hash equals `Hash(prefix + n)` for five seeds, five prefixes (including non-ASCII) and about 870 integers per prefix, including negatives, `int.MinValue` and `int.MaxValue`.
- On a 320-resident, 398-place city with mixed daily, overnight and weekly hours, run for three days in frame slices with car traffic, every `ActivityObserved` event (more than 5,000) compares `At` (all three overloads), `WorkOnDay`, `NextWork`, `CommutePreparationAt`, `DailyRhythm.OnDay` for two days, the employment draw, and `NextClose`, `NextOpen` and `Open` for four of the resident's places, at three to five minutes each. Every third check first drops the resident's cache. More than 200 leisure and 200 shop activities occur.
- Whole runs of the same city over four days agree byte for byte at every midnight (`SaveCodec.Write`) and in the full `ActivityObserved` stream (more than 8,000 events) across three variants. One runs one event per frame with warm caches. One runs three events per frame with every transient cache cleared before each frame, and is reloaded from its day-2 save. One uses `AdvanceTo` per day.
- `Choose` (with and without an eligibility filter and a null key) and `Shortlist` match on 120 origin and kind pairs.
- The opening cache matches the reference after each of ten successive hours edits (daily changes, list additions, in-place window edits, list replacement, removal and clearing) and when queries alternate between two days.
- `RoadTag` matches the `Split` parsers for all three call sites against three topologies, over 41 hand-written edge cases and 4,000 randomly corrupted tags.
- `TryMapRemainingSpans` equals `TryMapRemaining` field for field at every 1/37 of the route's duration. A route tagged for another topology does not map until its tags are rewritten, and a malformed tag fails the mapping.
- Warming the caches leaves `SaveCodec.Write` output unchanged and survives a round trip. `CloneForEvent` and `CommitEvent` carry the key cache. A changed identity ID or seed is never answered from it.
- After warm-up, 60 residents' routine queries for a day, 398 places' hours queries and 50 span mappings of a 40-leg route allocate exactly 0 bytes.

## Not verified

No game was launched and no rig was touched. The allocation and garbage-collection effect in Unity's Mono runtime, and any frame-time effect, are not measured. The byte counts come from .NET 10 on a synthetic city. The span overload of `int.TryParse` compiles against the game's assemblies, but I have not seen it run under the game's Mono. If that implementation parsed differently from the string overload, the `Split` comparison above would not reveal it, since the tests run on .NET. The harness planner, network and opening hours are synthetic and do not reproduce native route shapes, retimed fragments from a clock-rate change, or physical journeys; those paths are covered only by the existing unit tests and the road harnesses above. The pre-change copy used for the harness comparison was taken from the working tree at the start of this session, so it includes other sessions' uncommitted edits as they stood then.
