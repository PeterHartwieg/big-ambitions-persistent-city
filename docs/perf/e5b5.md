# E5b5 measurements

## 9 November 2026: offline components only

Foreground .NET 10 Release run on the Mac, timed with `Stopwatch`. The arms drive the Core code through the `ContractWorld` model (`tests/FoodContractCoordinatorTests.cs`) over doubles of the native objects. They are not combined mod-work or whole-frame samples. No game, rig, autosave setting or lease was used. The standing gate applies: combined mod-work p95 under 5 ms, every mod-work spike at or above 30 ms flagged, whole-frame timing reported separately. Rush and soak combined mod-work with eight-offer shops is rig check 6 in [the checks](../checks/e5b5.md#in-game-checks-for-the-next-batched-rig).

Command: `dotnet test tests/PersistentCity.Tests.csproj -c Release --filter "FullyQualifiedName~EightOfferCostsAndA1024ShopRecoveryWave" --logger "console;verbosity=detailed"`.

### Per-visit admission (`LiveMenu`, eight dynamic offers)

The only cost E5b5 adds to a discovery visit. 200 warm calls, 5,000 timed.

| p50 ms | p95 ms | max ms | B/call |
| ---: | ---: | ---: | ---: |
| 0.0021 | 0.0023 | 0.0338 | 0 |

Zero allocation is asserted (`LiveMenuRefusesEachMalformedShapeAndAllocatesNothing`). An all-original menu never reads the product policy, so original-three shops pay one `Known` loop, as before. In Runtime a dynamic menu also reads `FoodProductPolicySource.Current`, which on a clean read compares three references and returns the registry's cached publication under its lock.

### Selected capture and checkout, eight-offer shop

One owned eight-offer shop (three original, five dynamic), 1,200 capture-plus-checkout pairs, the first 200 discarded. Capture is `SupportedMenu`, the Decision 3 recheck and the supply read with Decision 5 reconciliation. Checkout adds the second recheck, the Q2 price verdict and the order.

| Step | p50 ms | p95 ms | max ms |
| --- | ---: | ---: | ---: |
| Capture | 0.0183 | 0.0540 | 1.6487 |
| Checkout | 0.0343 | 0.0616 | 1.5259 |

The model allocates (LINQ, dictionaries), and the maxima are GC pauses in the test process. The Runtime recheck itself measured 0.0065 to 0.0209 ms p95 at eight offers with 0 B in [E5b3](e5b3.md). Native `SetUp` and native supply reads are not in these numbers.

### 1,024-shop recovery wave

1,024 owned eight-offer shops (half with the menu reversed) are refused in one hour, handed back at the boundary, then prepared, rebuilt and recovered in the next hour.

| Units | Total ms | Mean unit ms | Recoveries | Max recoveries per frame | Frames at the 0.5 ms Runtime budget |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 3,072 | 22.0 | 0.0072 | 1,024 | 64 | 45 |

The model frame has no time budget, so its 17 frames ran at 5.6 ms each; Runtime stops each frame at 0.5 ms and requeues the rest. At that budget the wave takes about 45 frames, well inside one game hour even at speed 6. Every shop recovered, and reacquisition then commits 16 per boundary (asserted).

### Native `SetUp` count

Unchanged by construction. `NativeFoodMarket.SellLine` and `FoodSupplyReader.ReadMenu` stay the only two call sites (`NativeSetupCallSitesAreUnchanged` passes), and E5b5 adds no supply read. The Q2 price-only refusal happens after the setup that checkout already makes. In-game counts come from `nativeSetups` in rig check 6.

### Wins taken

None beyond the design: the policy is read only for a menu that has a non-original product, and `RefuseRemovedProduct` runs only when `SupportedBusiness` already failed and the shop's authority row is owned or wanted. The four parked hotspots stay parked.
