# E5b3 measurements

## 9 November 2026: offline components only

These numbers come from foreground .NET 10 Release runs on the Mac, timed with `Stopwatch`. They measure the Core code the coordinator runs, driven by the `ContractWorld` model in `tests/FoodContractCoordinatorTests.cs` over doubles of the native objects. They are not combined mod-work or whole-frame samples, and no game, rig, autosave setting or lease was used. The standing gate still applies: combined mod-work p95 under 5 ms, every mod-work spike at or above 30 ms flagged, whole-frame timing reported separately. Rig check 6 in [the checks](../checks/e5b3.md#in-game-checks-for-the-next-batched-rig) measures it in game, including native `SetUp`, whose cost is unmeasured offline.

Command: `dotnet test tests/PersistentCity.Tests.csproj -c Release --filter "FullyQualifiedName~RecheckBoundaryRebuildAndCommitGateCosts|FullyQualifiedName~ReconciliationAllocatesNothing" --logger "console;verbosity=detailed"`.

### Reconciliation (Decision 5)

128 holders, 1,000 timed calls: p50 0.0136 ms, p95 0.0153 ms, max 0.1080 ms, 0 B/call (asserted). It reuses the supply read's setup, so it adds no native `SetUp`.

### Native `SetUp` count

Unchanged by construction: `NativeFoodMarket.SellLine` and `FoodSupplyReader.ReadMenu` remain the only two call sites (`NativeSetupCallSitesAreUnchanged`), and reconciliation runs inside the read that already made the setup. E5b1's offline checkout workload (123 reads across eight shops, three sales) made 33 setups against 990 uncached ([E5b1 perf](e5b-complete-menu.md)). That workload's harness is a `tools/*-regression` suite and was not rerun. Rig check 6 records `nativeSetups` per window.

## Cheap wins

- **Reconciliation index.** The first `FoodHolderReconciliation.Check` matched every native entry against every image holder. At 128 holders that measured p50 0.2150 ms and p95 0.2487 ms (Debug). A per-image reference index and an epoch-marked array make it linear: p50 0.0072 ms, p95 0.0074 ms in the same Debug run, and 0.0153 ms p95 in Release. Still 0 B/call.
- **Frame budget estimate.** The first frame loop checked the budget after each unit, so frames ran past 0.5 ms by up to one unit (frame max 0.5100 ms at 1,024 shops). Stopping before a unit whose estimated cost would overrun brings the frame p95 to the budget. A budget-skipped recovery unit goes back to the queue instead of being dropped.
- **Tag reads.** The recheck reads authored tags through a bound `DynamicMethod` instead of `FieldInfo.GetValue` per call, so no reflection runs on the capture and checkout path.
