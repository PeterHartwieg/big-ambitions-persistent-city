# E5b4 perf: held-policy execution, 9 November 2026

Offline measurements on a Mac (Apple M1 Pro), .NET 10 Release test build, three processes each. These are not in-game mod-work numbers. Combined mod-work p95, spikes ≥ 30 ms and whole-frame timing come from the batched rig ([E5b4 checks](../checks/e5b4.md), check 6). Whole-frame timing and #128 stay separate. No game, rig, autosave setting or lease was used.

Reproduce:
- `PC_E5B4_MEASURE=<file> dotnet test tests/PersistentCity.Tests.csproj -c Release --filter HeldPolicyPerfTests`
- `PC_E5B4_MEASURE_LEGACY=<file> dotnet test tests/PersistentCity.Tests.csproj -c Release --filter OriginalThreeDecisionMeasure` (the same file also runs on an exported copy of the base `b8feb06`)

## Choice weight cost with 0, 8 and 64 dynamic offers

`FoodChoicePolicy.Select` over one 64-offer shortlist (8 shops × 8 offers, the largest a decision holds), with 0, 8 or 64 offers carrying a held revision-2 tuple. 4,000 timed calls after 200 warm-up calls. Each process runs the three arms twice and reports the second pass; the first lets tiered JIT promote the code (in a single pass the first arm ran at about 31 µs before promotion, which is JIT, not the policy).

| Process | 0 dynamic p50 / p95 | 8 dynamic p50 / p95 | 64 dynamic p50 / p95 | B/call |
| --- | ---: | ---: | ---: | ---: |
| 1 | 9.58 / 9.96 µs | 10.29 / 10.67 µs | 16.33 / 16.83 µs | 0 |
| 2 | 5.58 / 6.79 µs | 5.79 / 6.04 µs | 5.12 / 5.21 µs | 0 |
| 3 | 5.25 / 5.50 µs | 5.38 / 5.71 µs | 4.71 / 5.17 µs | 0 |

Process 1 is slower in all three arms, the legacy one included, so I read it as machine load rather than policy cost. Processes 2 and 3 agree, and in them the arms differ by less than 1 µs. A single weight call is 83 to 166 ns legacy and 83 to 208 ns with a held tuple, the same range. No arm allocates.

Steady path: 0 B added. `ThePolicyReadAndTheLegacyWeightPathAllocateNothingInSteadyState` gates it in the ordinary test run: 10,000 rounds of a clean policy read, `Select` over 8 legacy offers and a revision-2 weight allocate 0 B.

## Product policy

| Operation | Cost | Allocation |
| --- | ---: | ---: |
| `FoodProductPolicySource.Current`, no input changed (read once per new context) | p50 0 ns, p95 42 ns (timer resolution) | 0 B |
| `Executable` on a dynamic name | p50 208 to 250 ns | 0 B |
| `Capture` on a dynamic name (once per offer in a new context) | p50 541 to 584 ns | 40 B, the held tuple object; legacy capture allocates the same object |
| Rebuild after a new 2,000-name loaded image | 0.425 to 0.476 ms, once per catalogue revision | 46,920 B (the image itself is 261,488 B and belongs to E5b2) |

The rebuild happens only at the next new context after E5b2 publishes a new image, not per frame.

## Held metadata bytes at 64 tuples

64 revision-2 tuples at the widest values (fits 5,000, taste 0 to 4): 7,103 B written as JSON objects with property names, which is more than the compact wire stores. E5d's validator budget for 64 tuples is 2 + 64 × 36 = 2,306 B. Both are under the 8 Ki bound (`FoodNameIdentity.MaximumHeldWire` = 8,192).

## Cheap win: one held-shop lookup per candidate

`ContinueFoodDecision` used `d.Shops.First(s => s.BusinessId == c.BusinessId)` three times per candidate (ticket, memory contribution, alternative weight), and each call allocated a delegate. It now looks the shop up once and reuses it for the held tuple as well. Measured on a whole original-three decision (8 shops with croissant and burger, capture, quotes, choice and checkout; 40 timed decisions after 20 warm-up):

| Build | B/decision (three processes) | p50 / p95 |
| --- | --- | --- |
| Base `b8feb06` | 89,490 / 89,494 / 89,494 | 0.146–0.158 / 0.207–0.307 ms |
| E5b4 head | 88,118 / 88,118 / 88,118 | 0.155–0.165 / 0.238–0.296 ms |

1,376 B less per decision (−1.5 %). Time is inside the spread. The four parked hotspots stay parked.

## Gate

Every offline number above is far under the 5 ms mod-work gate, and no sample reached 30 ms. The E5b4 code runs once per new decision context (policy read, gate and capture) and once per candidate at evaluation. Nothing runs per frame. There is no reflection, polling or scan in a new hot path.
