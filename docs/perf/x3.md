# X3 performance: test suite only

X3 changes no mod code, so the standing gate (mod-work p95 < 5 ms, spikes ≥ 30 ms flagged, whole-frame timing separate) has nothing new to measure. This file records what the timing helper costs the test suite. [Checks and inventory](../checks/x3.md).

## Full suite wall time

Both runs used the same Mac (8 logical cores) and `dotnet test tests/PersistentCity.Tests.csproj`, one after the other, in the foreground. Other harness sessions kept the load average between 7 and 11 during both runs, so the two numbers are close to noise.

| Head | Tests | Duration (dotnet) | Real time |
|---|---|---|---|
| Base eb9e82f (detached worktree, removed afterwards) | 4,360/4,360 | 8 min 18 s | 499.6 s |
| X3 head | 4,370/4,370 | 7 min 57 s | 483.1 s |

The 10 new tests in `TimingBudgetTests` take about 3 s together. The two CPU-load tests account for most of that: about 1.3–1.6 s beside the load and 0.6 s for the slowdown test. These full-suite numbers are from the first head; review round 1 changed the helper (next section) and did not rerun the full suite, per the agent-speed rule.

## Extra runs the guard took

`PC_TIMING_LOG=<file>` makes the helper append one line per retry. Over the full run:

- Every real timing check passed on its first attempt. No check in the converted files retried.
- All 15 logged retries came from `TimingBudgetTests`, which fails on purpose. The 10× slowdown fails all 5 attempts, quiet (load factor 1.00) and beside the CPU load (factor 3.76 on attempt 1, then 1.44, 1.01, 1.01). The semantic tests' retries use a fixed factor.

## Review round 1: timed windows

The load factor now comes only from the `Start`/`Stop` windows, so each timed sample costs two thread-clock reads, outside its own timestamps. Three quiet runs each (macOS, load average 7–9 from other sessions):

| Test | Before round 1 | After round 1 |
|---|---|---|

Focused run: 197/197 passed (40 classes, 13 files). The retry log from that run held only the deliberate failures in `TimingBudgetTests`.

`GuardedWorkloadsPassBesideAFullCpuLoad` after round 1, three runs: spin p95 0.650, 0.410 and 0.888 ms at load factor 1.24, 1.44 and 2.04, one attempt each. The E5b3 workload passed beside the load each time with no retry. The 10× slowdown beside the load missed all 5 attempts; the log shows factors 2.62, 1.05, 1.65 and 1.68 for the first four (the last attempt is not logged).

The max checks against the 30 ms spike line take little help from the factor, which is one average over the attempt's windows; they rely on the retries. Nothing here has run on Windows, where the factor needs 250 ms of timed CPU time before it applies.

## Review round 2: per-check factor

Each check's factor now comes from its own kept windows; warm-up and discarded samples are left out. Recording a window goes into fixed arrays, so it adds no allocation. `Run` reads the thread clock once before the first attempt, because the first read in a process allocates 32 bytes.

- Focused run: 199/199 passed (40 classes, 13 files). The retry log held only the deliberate failures in `TimingBudgetTests`; it now prints, per missed check, the load factor of that check's best attempt.
- `RecheckBoundaryRebuildAndCommitGateCosts`, three quiet runs: 661–742 ms (683, 742, 661), against 682–687 ms after round 1. Same range within the noise of this busy Mac.
- `GuardedWorkloadsPassBesideAFullCpuLoad` passed in three runs beside the full CPU load.

On Windows, no current check reaches the 250 ms floor. The largest, the whole E5b3 test with its 23 measurements and setup, takes about 680 ms here, and each check now counts only its own windows. So every current check is retries-only on Windows. The first full run on the PC is the evidence that matters there.
