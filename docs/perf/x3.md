# X3 performance: test suite only

X3 changes no mod code, so the standing gate (mod-work p95 < 5 ms, spikes ≥ 30 ms flagged, whole-frame timing separate) has nothing new to measure. This file records what the timing helper costs the test suite. [Checks and inventory](../checks/x3.md).

## Full suite wall time

Both runs used the same Mac (8 logical cores) and `dotnet test tests/PersistentCity.Tests.csproj`, one after the other, in the foreground. Other harness sessions kept the load average between 7 and 11 during both runs, so the two numbers are close to noise.

| Head | Tests | Duration (dotnet) | Real time |
|---|---|---|---|
| Base eb9e82f (detached worktree, removed afterwards) | 4,360/4,360 | 8 min 18 s | 499.6 s |
| X3 head | 4,370/4,370 | 7 min 57 s | 483.1 s |

The 10 new tests in `TimingBudgetTests` take about 3 s together. The two CPU-load tests account for most of that: about 1.3–1.6 s beside the load and 0.6 s for the slowdown test. The helper's own overhead on a passing check is two thread-clock reads and two timestamps per attempt.

## Extra runs the guard took

`PC_TIMING_LOG=<file>` makes the helper append one line per retry. Over the full run:

- Every real timing check passed on its first attempt. No check in the converted files retried.
- All 15 logged retries came from `TimingBudgetTests`, which fails on purpose. The 10× slowdown fails all 5 attempts, quiet (load factor 1.00) and beside the CPU load (factor 3.76 on attempt 1, then 1.44, 1.01, 1.01). The semantic tests' retries use a fixed factor.

## Beside a full CPU load (one spinning thread per core)

Measured with `GuardedWorkloadsPassBesideAFullCpuLoad`, three runs:

| Run | Spin call p95 (5 ms budget) | Load factor | Attempts | Guarded part |
|---|---|---|---|---|
| 1 | 0.662 ms | 1.41 | 1 | 1.3 s |
| 2 | 0.662 ms | 1.70 | 1 | 1.6 s |
| 3 | 0.680 ms | 1.49 | 1 | 1.5 s |

E5b3's `RecheckBoundaryRebuildAndCommitGateTimings` (23 timed configurations) passed beside the load in every run with no retry. It takes about 0.6 s quiet.

In-process load on this Mac gave a load factor of about 1.5. I did not rerun the old bare assertions beside it. The PC failure on 9 Nov came from seven separate harness processes at 96% CPU, which this test does not copy. The 10× test shows the helper still fails a real slowdown when the factor is high (3.76).
