## F9b: declared game-assembly fingerprints (Decision 4)

- **`tools/acceptance/supported-game.json`**: named fingerprint sets, each the SHA-256 of the 27 assemblies `tools/build.py` references plus `Newtonsoft.Json.dll`. Hashes only. The first set, `steam-1331550-build-25482473`, was hashed read-only from this PC's installed Steam game (app 1331550, Steam build 25482473, `BigAmbitions.dll` dated 23 Sep 2026). `current` names it.
- **`tools/build.py --provenance <file>`**: an additive code path (two helpers and one `if` block; the existing lines are unchanged, no define or fault-point handling touched). After the existing missing-assembly checks and before compiling, it hashes the supplied assemblies and writes `{schema: persistentcity-build-provenance-1, managed: "<supplied>", set, differing[], assemblies{file: sha256}}`. `set` is the matching set's name, or `unknown` with the file names that differ from the closest declared set. No path is written. `unknown` never stops the build. A hidden `--fingerprints` option points at another declaration file (tests only).
- **Runner `build` stage**: runs `build.py ... --provenance {out}/build.json`, keeps the record as evidence and copies it into `provenance.game` (`supplied`, `managed: "<supplied>"`, `set`, `differing`, `assemblies`). With `unknown`, or no record, the summary adds a required native item `game-fingerprint` as `incomplete`; the build itself still passes. Without `--game-managed`, `provenance.game.supplied` is `false`.

## F9d: native-evidence ledger and rig manifest (Decision 7)

- **`tools/acceptance/native-assumptions.json`**: 17 rows seeded from existing records: save epoch (F7b), native save contract (F7), `BuyLive` sale authority (F1, A5), hourly settlement (F1), native clock and hidden skip, native shop inputs (F6a), agency billing (C5d), agency dialog (C5e), Street Food bridge (E6b, E6d), subway portals (F5g), world census (F5a), RLO donor contract, physical bodies (F2c, F2d, F5i), native road network (F2d), price response at weight 1.2, and the economy stage's two routed rows `native-staffed-throughput` (F6b check 2) and `native-wholesale-costs` (unscheduled until RIG-WHOLESALE). Each row has its records (records removed from the tree on 10 Nov are cited as `docs-history-2026-11-10:<path>`), `recordedAt` (the commit that added the record), dependent source globs, the section 7 rig check that proves it, the F8 capability ID (and F8f mechanism) where one exists, and `lastRigHead`/`lastRigFingerprint`/`lastRigEvidence`, all `null`: the 6 Nov batch passed only partial checks. The file also lists the section 7 checks with mode and rig capabilities.
- **`tools/acceptance/rig_manifest.py`**: reads the first-parent history once and counts, per row, the commits since its last rig evidence (or since `recordedAt`) that touched its globs: the row's debt. `stale` (rig evidence and debt, an evidence head outside this history, or a different fingerprint), `unproven` (no rig evidence) or `fresh`. A fingerprint other than the evidence's, or `unknown`, marks every row stale. "Native batch due" at debt ≥ 3 or on a fingerprint change. The manifest lists `f9-1` first, then the checks of stale rows, unproven rows and fresh rows (largest debt first), then `f9-10`; rows without a check are listed as unscheduled. `python tools/acceptance/run.py rig-manifest` runs it as a profile.
- **Runner**: `nativeEvidence` holds the ledger state (head, fingerprint, `batchDue`, stale and unproven rows, `requiredChecks`, per-row debt and touching commits, ledger SHA-256). With a ledger, the required native items are the rig checks of every row that is not fresh: each missing check is `not-run`, a merged failed check fails `native`. A rig stage satisfies a check by its `id` or its `checks[]`. The summary adds `nativeBatchDue`, `staleNativeRows` and `unprovenNativeRows` and never changes its verdict for them. `summarize` writes `{out}/native-assumptions.json` with the run's commit, fingerprint set and run ID for every row whose check passed from the same source; `--update-ledger` writes it into the repository file for a reviewed commit. No row is updated without a declared fingerprint set or when a rig file names another set than the build.
- **Ledger at this head** (`rig-manifest`, fingerprint `steam-1331550-build-25482473`): native batch due; 16 rows unproven, one unscheduled; 11 rows at debt ≥ 3. Order after the base merge (F9g touched the body paths): `f9-1`, `f9-8` (debt 28), `f9-4` (19), `f9-7` (7), `f9-2` (5), `f9-6` (5), `f6b-2` (5), `f9-5` (3), `f9-9` (3), `f9-3` (2), `f9-10`.

Without an implementation they compile away; an arm without bodies runs exactly as before.
- **`tools/acceptance/expectations/movement.json`**: `expectedRed` emptied. F2g recorded the green baseline: every one of its compared arms equals its reference, and its self-checks and E2 rows pass. F9a's movement tests assumed the red F2a baseline; they now build their red data from the 16 arm names F9a listed, and an unlisted differing arm fails against the empty list.
- **F2e's E2 replay arm** is already in the harness output (`e2`, 19 rows: the contact and visitor contact arms, replays from three checkpoints and five refusals), and the `movement` stage already fails on any failing `e2` row. - **Visitors**: `ActiveJourneyIndex.VisitorsReceiveBodies` is `true` at this base (F5i). Every body arm asserts the flag and that visitors received bodies under the same caps.
- **City stage filters** (`tools/acceptance/stages.json`, fix): F9a's `city-s`/`city-m` filters used `Category=city-s`, but F9c's facts carry `Trait("Size", …)`, so both stages matched nothing and reported `not-run`.
