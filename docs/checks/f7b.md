### What F7b adds

- **Side key `persistentcity:save-epoch_v1`** (`Persistence/SaveEpoch.cs`). Success value, newline separated, fixed order: `v1`, `sequence=N`, `schema=N`, `minute=R`, `population=KEY`, then one `payload=CHARS KEY` line per published PC key in ordinal order. Failure value: `failed:N`. The strict reader refuses unknown versions (`v2`, `v10`), non-canonical integers or minutes, empty or control-character text, unsorted or duplicate payload lines, a trailing newline, more than 16 payload lines or 4,096 characters, and a marker that does not list the population payload.
- **F5 contract.** `SaveEpochStore.PublishedKeys` is the one list of PC keys an epoch describes (today only `persistentcity:state_v1`). v1 readers check every listed key's exact length, whatever its name. If F5 person, wallet, employment or receipt-linked state ever leaves the population payload, it joins this list in the same epoch with no new marker key. Receipts and the authority manifest stay native-side keys in the same `modData` and are not copied (rule 8).
- **Binding and sequence** (`SaveEpochBinding`). Each attached session is bound to one `GameInstance` and its `modData` dictionary. Each callback gets the next sequence (continuing from the loaded marker; legacy saves start at 0). `CanPublish` runs immediately before the payload write, and again before the marker. It refuses a ticket that is closed, stale (a later callback started), for another or replaced save object or dictionary, or from a poisoned epoch. Once a failure marker is written, the session never publishes a success marker again.
- **Callback** (`SaveEpochCallback.Run`, wired by `Runtime/SaveEpochRuntime.cs`). It runs today's steps in today's order (`CaptureForSave`: accounting observations, RLO reread, `BeforeSave`, `CompleteCampaignsForSave`, `RefreshKnownOwnership`, input-epoch check, publication check, `SaveSession.WriteTo`) and then writes the success marker after the payload. Every non-publication path writes `accounting-stop_v1` (`save-epoch-failed`, first value wins) and then `failed:N`, keeps the previous payload, and stops PC through the F1 `StopAccounting` path. The stop now names the save-epoch cause in its status text. Every exception, including the ownership-release throw, is contained and native `Save` continues.
- **Re-entrancy (rule 5).** `Update` increments a unit depth around the whole city update. PC event units, checkout and `CompleteInitialization` all run inside it. Review round 1 (Sol-r1-1): the binding and the `onSaveGame`/`onGameUnloaded` subscriptions are now created in `TryStart`, before the initialization worker starts, in an *initializing* state. Until `CompleteInitialization` calls `SaveEpochBinding.CompleteInitialization()`, every callback refuses publication, writes both markers and stops PC, so a save while the worker is pending is never silently skipped. An initializing binding that fails or is abandoned (refused payload, replaced save object) unsubscribes and writes nothing, so load refusals still preserve every key. A callback with a unit or another callback on the stack writes both markers, takes no snapshot, and defers `StopAccounting` until the unit returns, so no runtime object is torn down mid-unit.
- **Detach (rule 9).** `Detach` first calls `DetachSaveEpoch`. If the bound `GameInstance` is still `SaveGameManager.Current`, it writes `accounting-stop_v1` (`detached-after-save`) and `failed:N` before any teardown. This covers `Fail`, `StopAccounting`, `Shutdown` (`onGameUnloaded`, `OnUnloadAsync`, `OnDestroy`). A verified replacement (another or no current object, as in `ResetPopulationForSaveChange`) writes nothing. After detach, nothing is written through that binding.
- **Load (rule 6).** `TryStart` runs `SaveEpochStore.CheckForStart` on the main thread before the worker. It refuses a failed, unknown-version, malformed or length-mismatched marker. The worker then compares the decoded payload's source schema, population key and exact minute with `DescribesState`. `CompleteInitialization` refuses if the marker reference changed during initialization. A refusal goes through `Fail` without touching `modData`. A payload with no marker loads under the existing rules, including `AccountingClock.Compatible`.
- **Diagnostics.** `PopulationRuntime.SaveEpochDiagnostics` is an on-demand projection (sequence, published, refused, last refusal, attached/detached, stop pending). No frame path builds it.

The **cross-build test** uses a frozen copy of the base startup refusal: stop-key presence, strict read and `Compatible`, ignoring `save-epoch_v1`. Every refusal case is refused by both the F7b start decision and that base copy, with the dictionary unchanged. A successful F7b save loads in both.

**Qualifications.** Native `SaveGameManager.Save`, `GameInstance` and the runtime lifecycle are test doubles. The doubles call the actual Persistence binding, callback, reader and `SaveSession`; a source-order test pins the real Runtime wiring to the same order and wiring points, but the Unity runtime itself is not executed offline. Mutation check: removing the detach marker write fails four lifecycle tests.

**Rule 7 finding.** The test shows that the minute-granular check alone accepts a stale same-minute payload (`Compatible(600, 600.5)` is true). Whether receipt reconciliation alone makes that pairing safe was **not** established offline. F7b no longer depends on it: every path that can leave a stale payload behind (failed write, re-entrancy, detach while current) writes both markers. The marker describes the payload by exact length, schema, population and minute, not by a content hash. A same-length, same-minute substitution by something other than PC would not be detected. PC itself cannot produce that pairing, because every PC non-publication path is marked.

**Behaviour changes from the base, all intended by the plan:** any save-callback refusal (RLO changed, write refused, exception) now stops PC through `StopAccounting` rather than a generic `Fail`. Any detach of a still-current city (runtime failure, mod unload, return to menu) marks its in-memory `modData`, so the city line is refused if the same object is saved again. Files already on disk are unchanged, which the save/quit/reload test checks. The order of native `onGameUnloaded` against a later save of the same object remains uninspected. The offline save/quit/reload test copies the file before detach, which *assumes* that order; it does not prove it. Rig check 2 below covers it.

**Native save/unload evidence (review rounds 1–3; owner decision, 5 November 2026).** Under merge rule v2 this slice merges after review and local tests. Native evidence for save/quit/reload, failure containment and the order of `onGameUnloaded` against a later save of the same `GameInstance` is batched into the next combined rig run, as checks 2, 4 and 6 below. This PR contains no native evidence, and the offline save/quit/reload test assumes that order rather than proving it. ## In-game checks for the next batched rig

Every check runs on the headless agent rig ([PeterHartwieg/big-ambitions-agent-rig](https://github.com/PeterHartwieg/big-ambitions-agent-rig)) in the **save-specific campaign** of plan section 7 (checks 1 and 4), except check 7, which belongs to ordinary batched windows. None is deferred to Peter, a playtest, an unlocked console or a by-hand check. Where the rig lacks a capability, the named capability is the extension to build.

1. **Coherent success pairs.** The rig loads a disposable FT city with an owned food shop (`shop_fixture`) and advances through natural purchases. It saves after a paid sale, with a receipt `Pending`, twice inside one native minute, and after a midnight posting unit, then reloads each save in a fresh process. It reads `persistentcity:state_v1`, `persistentcity:save-epoch_v1`, `accounting-stop_v1` and the receipt and authority keys from each checkpoint. It asserts a success marker whose payload length, schema 25, population key and minute match the payload, with sequences strictly increasing across the four saves, no stop key, PC active after reload (`SaveEpochDiagnostics.attached`), and native money/orders/stock (`money`, `shop_state`, `shop_log`) consistent with the PC receipts. — rig-automated (existing capability: `rig flow run`, FT `save`/`load`/`state`/`money`/`console`, `shop_fixture`, `shop_state`, `shop_log`; pending rig capability: **RIG-PCSAVE**, extraction of PC keys from a saved checkpoint plus semantic comparison).
2. **Save, quit to menu, reload.** After a normal save, the rig quits to the main menu (firing `onGameUnloaded`) and reloads that save in the same process and in a fresh process. It asserts normal start with no `accounting-stop_v1` key and a success marker matching the payload. The rig also records whether any native save of the same `GameInstance` follows `onGameUnloaded` (the save files' modification time and hash before and after quit). If one does, the rig reports a failure, because the plan then requires the alternative detach path. — rig-automated (existing capability: `rig flow run`, FT `save`/`load`/`state`; pending rig capability: **RIG-PCSAVE**).
3. **Relocation copy.** The rig triggers the native `LoadAsync` relocation branch on a saved F7b checkpoint and asserts that the relocated save carries the same payload and marker pair and loads normally. — rig-automated (pending rig capability: **RIG-PCSAVE** extended with a relocation-path trigger).
4. **Forced encode failure, then native progress.** On a disposable copy, the rig selects a PC test build with a declared fault point that refuses the population write. It saves, lets native play continue through more purchases, saves again natively, and reloads with the normal build. It asserts `failed:N`, `accounting-stop_v1 = save-epoch-failed`, a byte-identical previous payload (hash), the refusal message in the log, no exception escaping native `Save` (save file written, `.meta` present), and native play continuing. Then it loads the same file with a frozen pre-F7b writer-25 build and asserts refusal through `accounting-stop_v1`. It also loads an F7b success save with that base build and asserts normal start. — rig-automated (existing capability: RIG-MODSET DLL-set selection, FT `save`/`load`/`state`; pending rig capability: **RIG-FAULT**, including building the fault-point test variant; the normal F7b build has no fault point).
5. **Marker mismatch and unknown version.** On disposable copies of a success checkpoint, the rig sets the marker's payload length to N+1, `minute` to another value and the first line to `v2`. It loads each and asserts PC refusal with the reason logged and every `modData` key hash unchanged. — rig-automated (pending rig capability: **RIG-FAULT** checkpoint `modData` editing in a disposable copy, with **RIG-PCSAVE** key extraction).
6. **Runtime failure outside a save.** With RIG-FAULT forcing a runtime `Fail` outside a save (for example an injected `Update` exception), the rig saves natively in the same minute and reloads. It asserts `accounting-stop_v1 = detached-after-save`, `failed:N`, refusal on load in both F7b and the base build, and native play continuing. — rig-automated (existing capability: RIG-MODSET, FT `save`/`load`/`state`/`console`; pending rig capability: **RIG-FAULT**).
7. **No ordinary-play cost (ordinary batched windows).** In each ordinary performance window, with autosave verified off before the window (including after reload) and restored in cleanup, the rig asserts that `SaveEpochDiagnostics.sequence` does not change during the window (zero save callbacks). It records mod-work p95 (<5 ms) and every ≥30 ms spike, with whole-frame metrics kept separate. — rig-automated (existing capability: `rig flow run` autosave guard and health `autosave_disabled`, FT `state`/`console`; pending rig capability: **RIG-PERF-UNION**).
