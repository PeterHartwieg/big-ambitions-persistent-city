## What is implemented

### Schema 36 (Decision 9)

- `CityState.HeldPolicySchema = PlayerHoldSchema + 1` is the current writer. It has the same compact wire and entity shape as writer 35. The only difference is that it executes `FoodNameIdentity.DynamicWire` (`"held=2"`).
- `CityState.ExecutableMenuPolicy(schema)` names the one executable policy per writer: `DynamicWire` at 36, `FoodNameIdentity.Wire` for 25 to 35, E4's code policy for 23 and 24. `RequireExecutablePolicy`, the `CitySimulator` constructor, the header probe in `PopulationWire18` and the compact header probe all use it. So `DynamicWire` executes at 36 only, and writer 36 executes nothing else: a schema-36 city with `held=1` is refused by the save validator, the probe and the simulator.
- `MenuPolicy` defaults to the executable policy of the state's own schema until it is set. A new city is created at 36 with `DynamicWire`. A state relabelled to a frozen writer in tests reads that writer's policy, which keeps every frozen writer's bytes and pinned hashes unchanged.
- Writers 35 and older are refused by `SaveCodec.Read` with `DevelopmentSchema` and the "start a new city" message, and the store and session leave the payload byte for byte. A writer-35 city that held `DynamicWire` (readable there, never executable) is refused the same way. Writer 37 is `Future`. `LatestDevelopmentSchema` is now 35.
- New writer golden (`ChangeJournalTests.Fixture`): seed 5150 `12447cdf8cff62a2926452fb51550054bbcf681d89d6c310738988878d7226e5` (73,332 characters), seed 9217 `590df8dcc45df126fe97385fedcc5fcbe8ced21be6d57747246e9e8f1e3fc89e` (72,970). The writer-35 and writer-34 pins stay as they were and are now built through the frozen shapes (`DevelopmentChain.Write35`, `Write34`).
- At writer 36 a held revision-2 tuple must be class Food and must not name an original product (`ValidateNames25`). Older writers keep E5d's rule.

### Product policy (Decision 11)

- `Core/FoodProductPolicy.cs` (new): `IFoodProductPolicy` with `Executable(name)` and `Capture(name, traits, seed, consumer)`, and `IFoodProductPolicyMarket` for a market that supplies one. `FoodProductPolicy` is the immutable implementation:
  - `Executable` is true for an original product (`FoodProducts.Known`), or for a canonical name that is in the published loaded-name image and that the resolver classes as Food. Drink, Bundle, NonFood, Unknown, unloaded and non-canonical names are not executable. With no published image no dynamic name is executable.
  - `Capture` returns `LegacyFoodOfferMetadata.Capture` (revision 1) for an original product and `resolver.Capture` (revision 2) for an executable dynamic name. It throws for anything else.
  - `FoodProductPolicy.OriginalThree` is the policy of a market that supplies none.
- `Core/FoodWeightedCommerce.cs`:
  - `ProductPolicy()` reads the market's policy only when the city is at writer 36 with `DynamicWire`. Otherwise it is `OriginalThree`.
  - `BeginFoodDecision` reads it once per new context, inside the capture batch. The whole-shop gate uses `policy.Executable` in place of `FoodProducts.Known`. Each offer's metadata comes from `policy.Capture`.
  - `ContinueFoodDecision` never reads the policy. For an offer with a held revision-2 tuple it passes that tuple to `EvaluatedFoodOffer` (`metadata`, and the tuple's taste as `newTasteBand`). `FoodChoicePolicy.Select` then weighs it with the existing metadata overload (`Weight(..., FoodProductMetadata, ...)`). Revision-1 offers take the legacy overload as before.
  - The evaluation step now looks up the held shop once instead of three times. That is the cheap win in the perf record.
- `Core/FoodChoicePolicy.cs`: `EvaluatedFoodOffer` has an optional `Metadata` (a nullable struct, so no allocation). `Select` uses the metadata overload when it is present.
- `Core/FoodMealTickets.cs`:
  - `CandidateTicket` plans from the captured menu as held. It accepts an original product or a revision-2 Food offer, with the held taste for the latter, and never reads the current policy.
  - `CheckoutTicket` re-plans from the live menu as before. It admits extras through the current policy and resolves a dynamic extra's taste through it.
  - `RivalTicket` is unchanged.
- Rivals stay original-three: `FoodAlternativeObservation`, `FoodAdvertisedOffer` and `RivalFoodCatalogue` are untouched.

### Runtime composition

- `Runtime/FoodMarkets.cs`: `FoodMarkets` implements `IFoodProductPolicyMarket` with one policy for shop and vehicle scopes, so both channels hold the same names and metadata. `FoodProductPolicySource` builds that policy from three inputs: the config resolver, the API publication and the published loaded-name image. It rebuilds only when one of them is a new object, so a clean read returns the cached policy and allocates nothing. A null or refused image admits no dynamic name. If publication throws, the source falls back to `OriginalThree`, records `Failure` and logs it once as a warning. It retries only when the config or the image changes, or at the next city load, so a persistent cause costs no rebuild and no exception per context.
- `Runtime/PersistentCityMod.cs`: `ComposeFoodMarkets` passes a `FoodProductPolicySource` over `shops.LoadedNames`, `settings.FoodProductOverrides.Resolver` and `FoodProductMetadataApi.PublishSnapshot`. Both callers (lines 131 and 710 in the plan) reach the markets only through `ComposeFoodMarkets`, so this one argument covers them.
- `Runtime/FoodProductPolicyNames.cs` (new): a `NativeFoodMarket` partial with `LoadedNames => contractReader?.LoadedNames`, E5b2's published image. `Runtime/NativeFoodMarket.cs` itself is not edited.
- `Runtime/FoodProductMetadataApi.cs`: `PublishSnapshot`, the registry's publication alone, so the source can tell when the API image changed.

### Unchanged on purpose

Shops still admit only the original three until E5b5. `SupportedBusiness`, `MenuStatus`, `DynamicIntegrationRefusal`, `FoodProducts.Known` acquisition and `LiveMaximumOffers` are not touched (`git diff` shows no change to `Runtime/NativeFoodMarket.cs`, `Runtime/NativeFoodCandidates.cs` or `Core/FoodMenuPolicy.cs`). Vehicles keep `VendorRules.OriginalThree`. So at this head no live market offers a non-original product. The policy widens what Core accepts, and the first head that offers one (E6f or E5b5) exercises it in game.
