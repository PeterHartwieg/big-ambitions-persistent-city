Refs: the F8a local-test failure on 9 Nov 2026 (PC run 20261109-152420-pc-f8a-capability-model). `FoodContractCoordinatorTests.RecheckBoundaryRebuildAndCommitGateCosts` missed a wall-clock budget while the PC ran seven or more harness sessions at 96% CPU. The same suite passed 4,304/4,304 on a quiet machine.

## The rule

Every wall-clock value that a test compares against a fixed budget goes through `TimingBudget` ([tests/Support/TimingBudget.cs](../../tests/Support/TimingBudget.cs)).

Since the sync with #186, budgets are judged only with `PC_PERF_ASSERTS=1`, the switch `PerfGate` introduced. Without it, `TimingBudget.Run` runs the measurement once: the timed code and its exact asserts (bytes, counts, outcomes) run, and no budget is checked. With it, the rules below apply. #186 had replaced the same asserts with `PerfGate.Under`; at those sites this branch's `TimingBudget` code is kept, and `PerfGate` stays for any other use.

```csharp
TimingBudget.Run(timing =>
{
    // build state; keep exact asserts for bytes and counts
    var w = timing.Start();
    Work();
    samples[i] = timing.Stop(w, "recheck p95");   // wall-clock ms, as before; kept for this check
    timing.Under("recheck p95", samples[1899], 1.0);
});
```

1. Timed code sits between `timing.Start()` and `timing.Stop(window, check)`, and each kept sample's window is recorded under the check it feeds. Each check gets its own load factor from its own kept windows: wall-clock time over the test thread's own CPU time, never below 1. Setup, warm-up and discarded samples (`Stop` without a check), other checks' windows, sorting and reporting do not count. Where a sample is kept only after the fact, `End` closes the window and `Keep(check, sample)` records it. A busy machine keeps the thread waiting for a core, which adds wall time and no CPU time. A quiet machine gives about 1.00.
2. A check passes when `value / load factor < budget`.
3. If a check misses, the helper re-runs the whole measurement, up to 5 attempts, and judges each check on its best attempt. Load comes and goes. A regression does not.
4. Deterministic asserts (allocation bytes, counts, outcomes, hashes) stay ordinary `Assert` calls inside the closure. They throw at once and are never retried.
5. A check with no kept window gets factor 1: retries only.
6. `Run` reads the thread clock once before the first attempt. The first read in a process allocates (32 bytes on macOS), and the converted loops assert exactly zero allocations around their windows.

A code regression burns CPU on the test thread, so it raises the CPU time along with the wall time and the factor stays near 1. On a quiet machine the helper fails exactly where the old `Assert.True(x < budget)` failed, after four more tries.

The thread clock is `clock_gettime(CLOCK_THREAD_CPUTIME_ID)` on macOS and Linux, counted in nanoseconds. On Windows it is `GetThreadTimes`, which charges a thread whole scheduler ticks of about 15.6 ms. Short windows read 0 or one tick, but summed over many windows the count is right on average. So on Windows a check's factor needs at least 250 ms of its own timed CPU time (16 ticks); below that it is 1 and only the retries apply. No current check reaches that: the whole E5b3 test, 23 measurements with setup, takes about 680 ms on this Mac, and the other converted checks are of similar size. On Windows every current check is therefore judged on retries alone, which this file calls not enough by design under sustained load. The first full run on the PC is the evidence that matters there. On macOS and Linux the floor is 10 µs. Review round 1 dropped the first Windows clock, `QueryThreadCycleTime` converted at a measured rate, because Microsoft documents that its cycles must not be converted to time and a busy machine could skew the rate.

Limits:

- The factor cannot see timed code that sleeps, waits on I/O or works on other threads; that would overstate the load. None of the converted windows do any of those.
- A check's factor is one average over its own kept samples. That suits a p95, which load spread over many samples moves, and a single stalled sample among thousands barely moves the average, so a regression in the other samples still shows. For the same reason the max checks against the 30 ms spike line (E5b3 rebuild unit and commit gate, rush replay) rely mainly on the retries. Since review round 4 the E5b3 max checks use `MaxUnder`: a maximum is never judged below the CPU time of its costliest kept sample (capped at that sample's wall time), so a stall in one sample cannot discount a real CPU spike in another.
- `RushSpikeReplayTests` gets its times from `RushSpikeReplay.Run`, which tools/rush-spike-replay also compiles, so it cannot mark windows. It gets factor 1 and retries only. Since review round 4 it computes the uninterrupted hash once and compares every attempt's hash inside the measurement, so a cadence mismatch in a retried attempt fails at once instead of being discarded.
- The Windows path has not run yet. All evidence here is from macOS. `ThreadCpuClockRuns` fails on the first Windows run if the clock is missing. Because of the 250 ms floor, Windows gets retries only for every current check (see above).

Why not the alternatives:

- Retries alone were not enough by design. A sustained load like seven sessions on the PC can keep every attempt slow.
- A calibration loop measured before the test, used to scale the budget, measures a different moment than the workload.
- Judging each sample on its own CPU time would ignore a regression that blocks, and on Windows a single sample's CPU time is 0 or a whole tick.

### Retry safety

Each converted measurement must survive being run five times. Review round 1 found that the E6d lunch did not: a retry carried on from the minute the last attempt reached and ran past the vendors' 300-minute opening, so the exact checkout assert failed. The lunch now builds its own fixture, vendors and meals in every attempt.

To check every site, I temporarily changed the helper to retry each `Run` four times regardless and judge only the fifth attempt, and ran all 13 converted tests with `PC_E6B_MEASURE`, `PC_E6D_MEASURE` and `PC_E6E_MEASURE` set: 13/13 passed. The change was reverted before commit. The other E6d `Measure` calls share one fixture across attempts. They read, capture or buy from vendors with a million units in stock and do not advance the clock, so a repeat stays valid. E6e's `Measure` repeats its body actions on a shared fixture; it also passed the forced run.
