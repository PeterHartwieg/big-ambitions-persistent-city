# X3: load-tolerant wall-clock test assertions

Refs: the F8a local-test failure on 9 Nov 2026 (PC run 20261109-152420-pc-f8a-capability-model). `FoodContractCoordinatorTests.RecheckBoundaryRebuildAndCommitGateCosts` missed a wall-clock budget while the PC ran seven or more harness sessions at 96% CPU. The same suite passed 4,304/4,304 on a quiet machine.

Base: `codex/persistent-city` at eb9e82f (F9e #182, writer 36), reverified 9 Nov 2026 19:47. Test-only: no Core/, Runtime/, Persistence/ or tools/ edit, no schema change.

## The rule

Every wall-clock value that a test compares against a fixed budget goes through `TimingBudget` ([tests/Support/TimingBudget.cs](../../tests/Support/TimingBudget.cs)):

```csharp
TimingBudget.Run(timing =>
{
    // build state; keep exact asserts for bytes and counts
    var w = timing.Start();
    Work();
    samples[i] = timing.Stop(w);   // wall-clock ms, as before
    timing.Under("recheck p95", samples[1899], 1.0);
});
```

1. Timed code sits between `timing.Start()` and `timing.Stop()`. Over those windows only, each attempt measures a load factor: wall-clock time over the test thread's own CPU time, never below 1. Setup, warm-up, sorting and reporting between the windows do not count. A busy machine keeps the thread waiting for a core, which adds wall time and no CPU time. A quiet machine gives about 1.00.
2. A check passes when `value / load factor < budget`.
3. If a check misses, the helper re-runs the whole measurement, up to 5 attempts, and judges each check on its best attempt. Load comes and goes. A regression does not.
4. Deterministic asserts (allocation bytes, counts, outcomes, hashes) stay ordinary `Assert` calls inside the closure. They throw at once and are never retried.
5. A measurement that marks no window gets factor 1: retries only.

A code regression burns CPU on the test thread, so it raises the CPU time along with the wall time and the factor stays near 1. On a quiet machine the helper fails exactly where the old `Assert.True(x < budget)` failed, after four more tries.

The thread clock is `clock_gettime(CLOCK_THREAD_CPUTIME_ID)` on macOS and Linux, counted in nanoseconds. On Windows it is `GetThreadTimes`, which charges a thread whole scheduler ticks of about 15.6 ms. Short windows read 0 or one tick, but summed over many windows the count is right on average. So on Windows the factor needs at least 250 ms of timed CPU time (16 ticks); below that it is 1 and only the retries apply. On macOS and Linux the floor is 10 µs. Review round 1 dropped the first Windows clock, `QueryThreadCycleTime` converted at a measured rate, because Microsoft documents that its cycles must not be converted to time and a busy machine could skew the rate.

Limits:

- The factor cannot see timed code that sleeps, waits on I/O or works on other threads; that would overstate the load. None of the converted windows do any of those.
- The factor is one average over the attempt's windows. That suits a p95, which load spread over many samples moves. A single long preemption inside one sample barely moves the average, so the max checks against the 30 ms spike line (E5b3 rebuild unit and commit gate, rush replay) rely mainly on the retries.
- `RushSpikeReplayTests` gets its times from `RushSpikeReplay.Run`, which tools/rush-spike-replay also compiles, so it cannot mark windows. It gets factor 1 and retries only.
- The Windows path has not run yet. All evidence here is from macOS. `ThreadCpuClockRuns` fails on the first Windows run if the clock is missing.

Why not the alternatives:

- Retries alone were not enough by design. A sustained load like seven sessions on the PC can keep every attempt slow.
- A calibration loop measured before the test, used to scale the budget, measures a different moment than the workload.
- Judging each sample on its own CPU time would ignore a regression that blocks, and on Windows a single sample's CPU time is 0 or a whole tick.

### Retry safety

Each converted measurement must survive being run five times. Review round 1 found that the E6d lunch did not: a retry carried on from the minute the last attempt reached and ran past the vendors' 300-minute opening, so the exact checkout assert failed. The lunch now builds its own fixture, vendors and meals in every attempt.

To check every site, I temporarily changed the helper to retry each `Run` four times regardless and judge only the fifth attempt, and ran all 13 converted tests with `PC_E6B_MEASURE`, `PC_E6D_MEASURE` and `PC_E6E_MEASURE` set: 13/13 passed. The change was reverted before commit. The other E6d `Measure` calls share one fixture across attempts. They read, capture or buy from vendors with a million units in stock and do not advance the clock, so a repeat stays valid. E6e's `Measure` repeats its body actions on a shared fixture; it also passed the forced run.
