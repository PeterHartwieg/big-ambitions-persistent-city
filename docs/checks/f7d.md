# City audit F7d: compact save-wire writer (schema 34)

Refs #94. Plan: [F7 section 4, row F7d](../plans/f7-save-snapshots.md#4-slice-breakdown), sections 3.1, 3.4, 3.7, 3.8, 3.9 and 5. Format: [F7d compact-format decision](../decisions/2026-11-06-f7d-compact-format.md), candidate C. No migration: [no-migration re-scope](../decisions/2026-11-06-no-migration-rescope.md). Base `3f734cb` (F6i #150), writer 33. Measurements: [docs/perf/f7d.md](../perf/f7d.md). Persistent City is not live or released.

## What F7d changes

- **One schema bump.** `CityState.CompactSchema = ChangeJournalSchema + 1` (34) is the current writer. `LatestDevelopmentSchema` follows it to 33, so every schema from 1 to 33 is an older development city.
- **The compact wire** (`Persistence/CompactWire34.cs`). The save string is candidate C as decided: `{"Schema":34,"f":"pcc-c","v":1,"k":[keys],"h":[shapes],"s":[strings],"n":routes,"r":routeColumn,"t":rootColumn}` with the column grammar of `tools/compact-format/ColumnarCodec.cs` (tags 0 to 12): per-field columns, ordinal key, shape and string tables, exact number text or zigzag base-64 varints, a per-save route table that deduplicates `Journey` and `Route` values by exact content, and `ServiceId` road tags split into a topology head plus a chained node range. The one addition is the leading `"Schema":34`: every reader scans the top-level Schema first, so an older build reports a compact payload as Future and keeps it.
- **Encoded from F7c's snapshot.** `SaveCodec.Encode` validates the snapshot as before, then serializes it with the writer-33 body settings and converters straight into an exact token tree (no body text), checks the body's 256 Mi character and UTF-8 caps on that tree, and encodes the tree. The body is the writer-33 shape with Schema 34; F7d changes the encoding, not the entity semantics.
- **Strict reader.** `SaveCodec.Read` parses the compact string canonically (no whitespace, the writer's string escaping only, JSON number grammar), requires the exact envelope fields in order, format `pcc-c` and version 1, decodes the tables (strictly ordinal, no duplicates, every key and shape used, every route referenced) and the columns, writes the body back out and runs the existing strict body reader on it (token shape, every collection bound, no coercion, full semantic validation). Unknown tags, bad or negative table indices, dangling route references, route references or road ranges outside their fields, noncanonical nullable, mixed, shape or length columns, truncation and trailing text refuse. Bounds are checked before allocation: the input caps first, table entries against the 4,000,000-record cap before any table or route column, every column's values against `MaxCompactValues` (64 Mi) before its array, row arrays before their field columns, packed columns against their text length, and the body text is refused at 256 Mi characters before it grows past that. Table entries are charged one record each on top of the body's records, by the writer and the reader alike. String values are interned on decode (one instance per distinct text in the materialized city).
- **No migration.** A city written by any older schema, the JSON writers included (writer 33 too), gets `SaveReadStatus.DevelopmentSchema` with the "start a new city" message; its payload and every other key stay byte-identical, and neither publication path can overwrite it. Fresh cities are created in schema 34. `ReadWriter33` is the frozen writer-33 reader (unreachable from `Read`), and `ContractsFor(33)` names its frozen resolver. The JSON body codec is unchanged for schemas up to 33.
- **Header probe.** `RequireExecutableCapabilities` decodes only the envelope, the tables and the root's Schema, Capabilities and MenuPolicy columns of a compact payload; the route table and the rest are syntax-checked or never read.
- **Not in F7d:** F7e (overlap or worker encode), any history pruning (14 shop-history days and the 64-visit limit are unchanged), any change to the 256 Mi, depth, record, citizen, place or route-leg caps.

Test-side: `tests/SaveWire.cs` gives tests that edit a saved city as JSON its body (`SaveWire.Body`, `Text`, `Parse`) and encodes an edited schema-34 body back to the compact wire (`SaveWire.Payload`, `Read`), so each edit is still judged by the full strict reader. Older-schema JSON and canonical compact strings pass through unchanged. `DevelopmentChain.Write` returns the body for current-schema cities. The F6g writer-33 golden test now pins the frozen writer 33 (same two hashes). Four error-message expectations changed where the compact wire refuses earlier (`01` is not a JSON number; a duplicated body field is a duplicated shape field; the writer refuses a converter's raw JSON). Assertions that the current schema is 33 now say 34.

## In-game checks for the next batched rig

These come from F7 plan section 7 checks 1, 2, 3, 5 and 6, made testable for F7d. All belong to the save-specific campaign and run only when it is requested, never inside a clean gameplay window. Each runs on the headless agent rig in a disposable FT city; autosave is recorded, set off and restored as AGENTS.md requires. Because there is no migration, every before/after pair uses a fresh city created from the same seed by each build, never one checkpoint loaded by both. None is deferred to Peter.

1. **Compact save epoch coherence (plan check 1).** Setup: a fresh disposable FT city created by the F7d build, with an owned food shop. Steps: advance through natural purchases and save just after a paid sale, with a receipt `Pending`, twice inside one native minute, and after a midnight posting unit; reload each save in a fresh process; finally make a normal save, quit to the main menu, and reload that save in the same and in a fresh process. Expected: `persistentcity:state_v1` starts with `{"Schema":34,"f":"pcc-c","v":1,`; the epoch marker names writer 34 and the payload's exact length; PC wallets, receipt states, ownership and minute describe the same epoch as native money, orders, stock and statement; the city loads with PC active after quit to menu with no `accounting-stop_v1` key. — rig-automated (existing capability: `rig flow run`, FT `save`/`load`/`state`/`money`, `shop_fixture`, `shop_state`, `shop_log`; pending rig capability: **RIG-PCSAVE** payload and marker extraction).
2. **Save phase cost before and after (plan check 2).** Setup: two fresh FT cities from the same seed, one created by the base build `3f734cb` (writer 33) and one by the F7d build, each at the 957-resident representative load and at the F5 declared load (1,914 and 2,871 persons); save-cost diagnostics requested. Steps: `Default`, `MidnightSave` and `RecoverSave`, five each, reading the save-cost record after each. Expected: native `Save` total, each PC phase (synchronize, capture, validate, encode, publish), native `SerializeSaveGame`, portrait/screenshot and compression thread recorded for both builds; payload characters about 0.35 × or less of the writer-33 payload with UTF-16 bytes = 2 × characters; every phase ≥ 30 ms flagged as a save sample, never mod-work. — rig-automated (existing capability: `rig flow run`, FT `save`/`console`; pending rig capability: **RIG-SAVEPROF**, **RIG-SAVETYPES**).
3. **Interrupted save and reload in the compact format (plan check 3).** Setup: an F7d FT city at the RIG-CHECKPOINTS states: a pending route answer, posting units stopped after 32/64/96, a held meal decision, an outward excursion, the morning rush with journeys in flight (route table in use), a queued campaign publication, a visible physical lease, a receipt `Pending`. Steps: save at each state, continue 30 game minutes, reload in a fresh process and continue 4 game hours at another frame cadence against an unbroken control; separately kill the process during native serialization (arm a) and during compression over a reused name (arm b), each after saving a known-good checkpoint under a different name. Expected: ledgers, journeys, queues, receipts and identities equal the control; nothing counts as finished twice; arm (a) leaves the destination's bytes and hash unchanged and it loads coherently; arm (b) either fails native load or is refused by PC with every key kept, and the separate checkpoint loads with an unchanged hash. — rig-automated (existing capability: FT `save`/`load`/`state`/`time`, `rig flow run`; pending rig capability: **RIG-CHECKPOINTS**, **RIG-PCSAVE** comparator).
4. **Older cities refused, newer payload preserved (plan check 5).** Setup: a disposable FT city saved by the base build (writer 33), the `pc-schema-25-ref@1` and `pc-schema-13..16@1` fixtures once produced, and an F7d save. Steps: load each older city with the F7d build; load the F7d save with the base build; load a truncated and an over-cap copy of the F7d save with the F7d build. Expected: every older city shows the "start a new city" refusal (`DevelopmentSchema`), takes no food ownership, and its `state_v1` string and every other key are byte-identical after the session and after a native save; the base build reports the F7d payload as Future and keeps it; the damaged copies are refused as invalid with every key kept. — rig-automated (existing capability: fixture library manifests, RIG-MODSET DLL set selection, FT `save`/`load`/`state`; pending rig capability: **RIG-PCSAVE**, plus production of the `pc-schema-N@1` fixtures).
5. **Large-city compact save (plan check 6).** Setup: fresh 10,000-consumer and 50,000-resident FT cities created by the F7d build from a fixed seed, and the same seeds created by the base build. Steps: three manual saves each with diagnostics requested, then reload the last one in a fresh process. Expected: each save publishes under the caps; capture, validate and encode recorded and flagged when ≥ 30 ms; peak process memory during save and load recorded; payload characters at most 40 % of the base build's at 50,000; reload restores the same resident, visitor and place counts and the same population key; off-thread decode and main-thread `CompleteInitialization` recorded. — rig-automated (existing capability: `rig flow run`, FT `save`/`load`/`console`; pending rig capability: **RIG-SAVEPROF**, and a fresh-city builder for a 50,000-resident current-schema FT city in place of the migrated `city-50k@1`).
