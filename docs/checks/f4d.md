Refs [#91](https://github.com/PeterHartwieg/big-ambitions-persistent-city/issues/91). Branch `codex/pc-f4d-batch-flow` from `origin/codex/persistent-city` at `17dccf8` (E6f #185; F4a #178, F4b #175 and F4e #176 merged). Scope: the F4d row of [the F4 plan](../plans/f4-perf-gate.md#4-slice-breakdown), with Decisions 1, 2, 3 and 8 and section 7 as its spec. [Perf](../perf/f4d.md).

F4d adds tools and tests only. No Core, Persistence or Runtime file changes, and no F4a, F4b, F4c or F4e file changes. The writer and the pinned current-writer golden hash are untouched. No schema change and no migration. The generator writes a flow and runs nothing. All results below are offline; none is game evidence.

## What is implemented

All in `tools/perf-gate/`:

- **`fixtures.json`**: Decision 2's four fixtures (FT-F4-Declared, FT-F4-Stress10k, the fastest-traveller arm, the dependency-only reference) with content, purpose, expected population, business load, PC config, provenance and preparation steps. Also Decision 1's declared settings, the declared pace (factor 1/3, speed 1, 3.3 real s per game minute) and Decision 3's window conditions with their repetitions and scripts.
- **`scripts/`**: one step list per Decision 3 script (`S-stationary`, `S-path`, `S-sweep`, `S-drive`, `S-manage`) plus `S-session` for G13. Each has `setup` steps (before warm-up), `loop` steps (repeated until the window stops), optional `teardown` steps and `samplers` (S-path reads `screen_pos list` every 10 s and the physical diagnostics line every 60 s for density). A step can be limited to one build: the reference arm of S-manage opens the native screens only.
- **`make_gate_flow.py`**: `python tools/perf-gate/make_gate_flow.py --out <flow.json> [--md-out <flow.md>] [--movement-state <label>]`. Writes `perf-gate-flow/v1`, deterministic for the same inputs. Exit 2 with `REFUSED: <reason>` and nothing written for an unknown op, a script whose name does not match its file, a duplicate window or a process whose first window is not a prime.
- **`test_make_gate_flow.py`**: 43 tests.

### Flow shape

Each step has an `id`, an `op`, the `checks` it serves (G1–G15, `fixtures`, `cleanup`), its game `process`, `build`, `window`, `args`, and `capabilities` split into `existing` and `pending`. The capabilities come from one op table in the generator; a `script.run` step carries the union of its loop and sampler steps. The flow also lists the capability catalogue, a per-check summary (steps, windows, existing, pending, and pending capabilities that come from fixture preparation), an index of pending capabilities, the processes and the windows with the export labels F4a reads (`condition`, `script`, `build`, `arm`, `repetition`, `native_speed`, `checkpoint_minute`, `first_in_process`, and `${fill}` for the measured fields).

Batch order follows section 7: G1 preflight, fixture preparation, G2, G3, the G4–G8 matrix, G9, G13, G14, G15, G10, G11 analysis, cleanup. G12 is excluded: it is a separately requested save-specific segment and never part of this flow.

### Decision 3 rules, by construction

- **Fixture production.** The producer owns its lifecycle, like `produce_fixture.py`: it needs no player running and no lease held, takes its own lease, refuses an existing save name and keeps its saves. `produce_fixture.py` itself cannot produce this fixture: it accepts only `FT E5b ` names and refuses a Ready save whose schema is not 25 (`tools/e5b-native-rig-proof/produce_fixture.py`, around line 216), while the candidate writes the current schema. So production names the pending capability RIG-F4-PRODUCER, a current-writer adaptation. The flow runs the read-only G1 identity steps first, then the producer, then `rig.lease acquire`, and only then the G1 steps that change the profile (autosave record and disable, settings, PC config record, sampler). G1 therefore records the original settings after the producer has restored the profile. The save names carry the run id (`FT F4 Declared ${run}`, `... Ready`; `--run-id` fills it, or the batch does), so every batch and retry asks for new native names. Preparation loads the Ready save and saves the checkpoints as `FT-F4-Declared@d3-HHMM`.
- **Preparation chronology.** The anchor survey needs 18:00, but the first checkpoint is 02:30. Preparation saves `FT-F4-Declared@prep` at day 3 00:30, runs the survey on a disposable copy, reloads the preparation save (with its autosave check), then advances forward through the checkpoints. Stress10k does the same.
- **PC config.** G1 records the profile's original PC config. Every candidate process applies the complete declared config (factor 1/3, caps 48/24, radius 120, bodies on), overlaid with its arm's changes (factor 1 for the fastest traveller, caps 256/64), before launch, and reads it back. Cleanup restores the original. Reference processes have no PC config.
- **Autosave.** G1 records the original setting once and disables it. An autosave check follows every launch and every load and comes right before every window and segment starts. Cleanup restores the setting and reads it back.
- **Save receipts.** Candidate windows read `SaveEpochDiagnostics.sequence` at start and check it unchanged at the end. Every probe window, in both builds, also checks the probe's native `onSaveGame` counter (`saves_in_window = 0`, reset at measure-start) after measure-stop. The reference has no Persistent City projection and uses only the probe counter.
- **Load and arm.** After each load the flow waits for the native load to finish, then arms the probe (F4b refuses to arm during a load), then checks readiness.
- **Warm-up.** Each window first sets its native speed, then runs script setup, readiness (candidate: simulation ready and accounting no longer held; reference: pace shim active), 60 real seconds discarded, and the start-minute gate. So warm-up and the gate run at the measured pace whatever speed the checkpoint was saved at.
- **Window length.** Matched windows (both builds) stop at a fixed span of 118 game minutes since start, so reference and candidate cover the same game minutes for F4a's P4 match. The span covers the 300 s clean floor plus 10 % even at 85 % of the declared 3.3 real s per game minute (fast_pace_fraction); at the declared pace it is 389 real seconds. A matched window that still ends with fewer than 300 clean seconds is reported short and does not count. Candidate-only windows (256/64, stress, G13, G14) stop only when both the clean floor and their span are reached. A window that runs past twice its planned time is aborted and reported short. Probe frames are drained every 30 s so the rig can count clean seconds.
- **Same start minute.** Each window checkpoint is saved 30 game minutes before the window start. After warm-up the flow waits for the game clock to reach the start, so both builds start at the same game minute (F4a's P4 match). A clock already more than 1 game minute past the start aborts the window.
- **ABAB.** For each window × script, repetition r runs the reference, then the candidate: two repetitions per build, four for W-morning and W-evening. A build switch needs a new mod set, so each repetition and build is its own game process. Each process runs every script of its window, reloading the checkpoint before each.
- **First window per process.** Every process starts with a 120 s prime window, labelled `first_in_process` so F4a discards it, and then reloads the checkpoint. G10's latency segments are the exception: they measure a fresh process on purpose.
- **Reference arm.** It loads disposable copies marked `never_save`, uses the mod set without Persistent City, arms the probe in reference mode at the candidate's factor, and has no save step and no Persistent City read. Saves happen only in fixture preparation, outside windows, in the candidate build.
- **Run header.** Every Decision 8 field and the I1 fields (logical population, business load, calendar pace, observed body load) name the step that fills them. `movement_state` comes from `--movement-state`, or the G1 step fills it: `movement=pre-F2d` unless the candidate contains F2d (`ece4878`, #169), then `movement=F2d`, or `movement=F2e` with #172. Each field says where it is required. `header.require`, before the first timed step, checks every field except `observed_body_load`, and each of those fields is filled by an earlier step (calendar pace is the declared pace; the probe adds the measured pace per window). `observed_body_load` comes from the window samplers and is required when each export is assembled. A missing field stops the batch.
- **Stopping early.** Cleanup steps carry `on_stop: true` and form the tail of the flow. If the batch stops early (`header.require`, an abort, an error), the rig runs them in order: player stopped, sampler stopped, mod set, PC config, settings and autosave restored and read back, fixture copies removed, inputs verified, rig files restored, lease released.
- **Probe labels.** F4b accepts window labels of letters, digits, `-`, `_` and `.`, at most 64 characters. Each window keeps its report ID (for example `W-evening@High.S-path.report-only.reference.r1`) and gets a `probe_label` with `@` mapped to `_`, used for measure-start and the trace. The export labels carry both.

### Choices where the plan left room

- **W-accounting** is not its own checkpoint. It is the native hour rollovers inside W-lunch (12:00, 13:00) and W-evening (18:00, 19:00) with the owned shops open, plus W-midnight. Those S-stationary and S-path windows carry G8.
- **Window spans** start at the plan's start times and run 118 game minutes, so W-morning covers 07:00–08:58 instead of 07:00–08:30. The 300 s floor needs about 91 game minutes at the declared pace.
- **S-manage runs at W-lunch** (G7: player inside an owned shop at lunch). The run budget sentence lists it under W-evening; G7 is the more specific spec.
- **Secondary arms.** The High preset (Decision 1) runs W-evening S-path ABAB with two repetitions as `report-only`, condition `W-evening@High`. The 256/64 cap arm runs once, candidate only, as `report-only`, condition `W-evening@caps-256-64`. FT-F4-Stress10k runs W-morning, W-evening and W-midnight S-path once each, candidate only, as `stress`. The condition suffixes keep F4a from refusing two windows with the same label.
- **Export groups.** G2/G3, the gate matrix with its secondary arms and G15, G9, G10, G13 and G14 go into separate exports, so G13's and G14's candidate-only windows do not leave P4 open in the matrix verdict.
- **Anchors.** The flow names kerb points and waypoints (for example `dense-street.wp1`, `sweep.kerb-3`). Fixture preparation records their positions once, by the rule in `fixtures.json`, and every build reuses them. Every anchor a script uses, including owned shop 1's door and inside point, is in its fixture's survey list (tested).

## Known limits

- The rig executes the flow. Assembling each export group into `perf-gate-export/v1` is a named host step (`host.assemble_export`); the converter from probe pages and trace CSV to that shape is not part of F4d.
- `host.attribute` names F4c's classifier (PR #189), which has not merged.
- Run-time figures are estimates from fixed per-step allowances (see [perf](../perf/f4d.md)), not measurements.
